# Add a Domain Pack

The normative format is [docs/specs/domain-pack-format.md](../../../docs/specs/domain-pack-format.md) (file layout, features and tiers, feature gating, YAML pitfalls); package overview: [docs/packages/content.md](../../../docs/packages/content.md). Packs are data in `packages/content/src/mde_content/data/packs/<archetype>.yaml` (shipped: `commerce`, `food_delivery`, `booking_services`, `internal_workforce`, `custom`). The shared recipe library is the single file `data/recipes.yaml`; themes are `data/themes.yaml`; the Stack Profile is `data/stack-profile.yaml`; policies are in `data/policies/`. Archetype ids are strings, never Python literals.

1. **Choose the archetype id** (snake_case, unique). For anything without a pack, `custom` composes base recipes (auth, profile, settings, list, detail, form, search, notifications, empty/error/loading) plus the chosen features.
2. **Author the pack.** Features (`id`, `label`, `tier` core, standard or extra, `default_on`, `i18n.hi`), roles, enums, entities with fields, API operation skeletons, integrations (mock, adapter or real; mock by default), compliance triggers (health, finance, children, identity documents, precise location), screens each mapped to a recipe, flows (one primary), the navigation tree (screens referenced as `"@key"`, a `PackNavNode`), and the `feature_parts` sidecar for the pieces that exist only when a feature is on. Use only recipes from the library; if none fits, add a recipe first.
3. **Everything the pack references must exist**: recipes, entities, roles, screens used by flows, themes (`theme_candidates`, the first is the default). Every pack screen has a recipe; every flow resolves; navigation routes equal screen routes.
4. **Wire the questions** with the `add-question-card` skill: add the archetype to `catalogs.yaml`, then its card file, so the `scope.features` checklist offers **exactly** the pack's feature ids with the same pre-ticked set (`default_on`); cover every `must` slot, add six starter chips, one inspiration card and a resolution card for each contradiction.
5. **Check the Stack Profile.** Anything the pack needs that needs a development build is flagged there; unsupported types (games, AR, desktop, background audio, hardware-heavy) stay unsupported. Do not invent an Expo SDK number.
6. **Validate**: `uv run pytest packages/content` (the pack tests run `validate_pack` on the full pack and on every feature selection and check the screen count, 25 to 45 with a cap of 50, the primary flow, feature ids, themes, flag and card ids and the round trip through the contract models; the bundle test checks that catalogs, packs and banks agree). Then check that the baseline expands to a valid spec: `uv run pytest packages/spec-builder -k baseline`.
7. **Evals and prompts**: add the golden brief for the archetype under `evals/datasets/briefs/<archetype>/` (then `uv run python -m evals.runners.make_goldens` and review the diff) and its offline research fixtures in `packages/prompts` (an archetype entry in `calls/s1_web_search/fixtures/search.yaml` and in `calls/c8_synthesize_research/fixtures/drafts.yaml`; the C8 draft must name real feature ids from the pack).
8. **Docs**: update `docs/packages/content.md` (and `docs/specs/domain-pack-format.md` if the format changed). Rules: `.claude/rules/content.md`. A contract change (a new field on `DomainPack`) is a request to the lead, never an edit.
