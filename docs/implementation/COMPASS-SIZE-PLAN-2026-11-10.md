Branch `feat/compass-speed-v3`. Written 2026-11-10 from a read of the code, the two real exports in `docs/compass/outputs/` and an independent review of the first draft against the code; approved by the owner the same day with three additions (a large app must be sufficient for 50-60 screens, the Brief must guide research depth by app size, the final Brief must be logically correct and realistic; live testing allowed within the USD 3.00 ceiling). Phase A is sections 2 to 5f, Phase B is sections 6 to 8a. Decisions: D-113 to D-120; ADR: [0017](../adr/0017-brief-structure-sections-and-size-bands.md). Progress is ticked in `PROGRESS.md` ("Compass size").
Hard rule 12 applies (no questions to the owner): every choice is made and logged; owner-visible assumptions are in section 9.

## 1. Context

The downstream AI that writes React/Expo from the Brief needs modules, a screen inventory, flows, entities, role access and
checkable consistency. The Brief has none of that as typed data. The owner wants the three tiers to mean APP SIZE
(7 -> small 8-15 screens, 12 -> medium 20-30, 25+ or a document -> enterprise 40-60+), with the AI drafting the breakdown and
the user approving it at Gate 1 (module by module for big apps). Outcome: a Brief that can describe a 60-screen app, sliceable
by module, with hash-safe storage, tests per phase, no hash churn for stored Briefs, speed first, USD 3.00 ceiling untouched.

### 2.1 Where I disagree with the recommendation, and why

1. Agreed: question count sets effort and target size, NOT the level of detail. Same record schema at every tier; only counts and review strictness differ.
2. No hard per-tier minimum counts. A 5-screen app must not be padded. Bands are target guidance to the generator plus warn-only checks (below band: silent; above band x1.25: recommend the larger band). "Required sections per tier" = none: every tier gets every section.
3. A document does not automatically mean enterprise. Band = max(tier band, band from the document's verified claim count); thresholds in data. A one-page brief should not force a 60-screen plan.
4. Drop from the owner's list (belongs to later stages or is supplied by recipes): routes, navigation tree (derive edges from flow steps, in code), API operations, lifecycle transitions, per-screen sections/bindings/copy, empty/loading/error states (recipes supply them; only deviations matter, and those stay facts), GIVEN/WHEN/THEN. Keep brand/look, locales, a11y, offline, compliance where they already live (slots and fact kinds).
5. Add to the list: `serves` (screen -> feature, traceability), `entities` on screens (what data a screen reads or edits; makes "every entity is used" checkable), entity `states` (a short list, because status drives screens), module `entry` screen, and per-flow acceptance lines (acceptance per feature = acceptance of the flows that serve it).
6. Phase (v1 vs later) is DERIVED in code from the feature priority the user already set in the closing question (must = core); the model never assigns phases.

### 3. Boundary and representation decisions

#### 3.1 Boundary (ADR 0017 states it; doc 11 gets section 17.10)
Compass drafts a user-approved STRUCTURE at intent level with the Spec Graph id prefixes (MOD, SCR, FLW, ENT; doc 04 section 1) so the later
Blueprint inherits ids instead of re-deriving. Safeguards: AI-drafted items are `Default` tier with provenance `model_knowledge` (never Locked
by the model); Locked only when a user or document fact supports the item (`user_text`/`document` evidence); Approve All never creates Locked;
the structure is drafted before Research, so the later Blueprint may add research-tagged items and fill lifecycles, rules, operations, navigation tree,
per-screen detail. When a Brief carries an approved structure, doc 03's G1.5 can be treated as satisfied for those sections (noted, not built here).

#### 3.2 Representation: four new optional Brief list sections, NOT DomainFact
`modules`, `screens`, `flows`, `entities`, each a list of `ItemMeta` records, engine-owned.
Why not `DomainFact.kind` + `refs` for the bulk:
- A fact is a projection of the ledger with a verified quote; `domain_facts` is READ_ONLY ("change the answer"). AI-drafted screens have no quote.
- Typical details are drafted as assumption-origin facts capped at 12 (D-110): the mechanism was built for a handful, not 60.
- A statement string cannot hold module/roles/steps/fields, so code could not check "every flow references existing screens".
- FCT ids are ledger ids, not stable structure ids; the duplicate-fact problem (53% of Pune rows) would be copied 60 times into the views.
- One section hash per record type gives clean "changed since approval" diffs.

`DomainFact.kind + refs` stays for rules, numbers, acceptance, compliance, nfr, constraints, examples (no new kinds), and `refs` may now point
at MOD/SCR/FLW/ENT ids (extend `compile_apply.resolve_refs` to resolve them when present).

Hash safety (proved by code reading; pinned by tests):
- `brief_hash` drops every `OPTIONAL_SECTIONS` entry that is empty; `section_hashes` skips it. So a Brief that never held a structure hashes exactly as before.
  Needed edits (enumerated by grep and by the review): `Brief` fields, `SECTION_KEYS`, `OPTIONAL_SECTIONS`, `ID_PREFIXES` (MOD, SCR, FLW, ENT as local constants: `compass-isolated` forbids importing spec modules), `known_ids`,
  `views/paths._VIEW_SECTION_BY_ROOT`, `views/diff.py` (generic), `engine/validate.py` (`_id_problems` and `_reference_problems` must know the new refs: serves, roles, entities, steps, access), `SECTION_STRING` in `service.py` (change summaries), the Brief-view row builder (`views/build.py` indexes `rows_by_section[sid]`, so a new `SectionId` without a builder is a `KeyError`), and the registries of `engine/patch.py` (`RECORD_MODELS`, `PREFIX_BY_SECTION`; an unregistered section is a bare `KeyError` that is not a `PatchError` and crashes the turn). `NAME_FIELD` gets modules, flows and entities but NOT screens (it triggers a section-wide duplicate-name rejection; "Order details" legitimately exists in two modules; per-module uniqueness is a structure check). `PROBES_BY_SECTION` is deliberately NOT extended (the probes do not read the structure, and every Accept would otherwise run model calls and could push Approve All into `_open_review`).
  The four sections are NOT in `READ_ONLY_SECTIONS` (unlike `domain_facts`): `_undo` replays `inverse_ops` through the same `apply_ops`, so read-only would break undo. `apply_slots` and `sync_assumptions` deep-copy and keep non-slot sections, so `_rebuild`, undo, pivot and answer edit do not reset them (verified).
- Reversibility: `Strict` forbids extra fields and `model_dump` always emits `modules: []`, so a Brief saved after this change would be unreadable by reverted code. The four fields get an omit-when-empty serializer on `Brief` (same device as `DomainFact._omit_empty_detail`); `section_hashes` reads `data[key]` today and must switch to `.get` (the key may be absent). Briefs that DO hold a structure cannot be read by reverted code: a revert after a live run strands those sessions (owner-only live sessions; stated in the hand-off).
- No `SCHEMA_VERSION` bump (it lives in hashed `meta`; a bump moves every hash). No new hashed `meta` key: band, source and counts go in `meta.interview`
  (`InterviewBlock`, already popped from the hash; `_commit` already saves when only it changes).
- No new field on `FeatureRecord`/`RoleRecord`/any existing record (that would move the hashes of every Brief with features).
- Verified today (read-only script): the current code reproduces the stored `_hash` and `_section_hashes` of BOTH real exported Briefs, and the Pune `approved_baseline` hash and section hashes, so the pin tests below are feasible and use real data (an approved Brief with its approvals). The Brief is a JSONB document in `compass_brief_versions`, so no migration is needed (rule 7).
- Tests: (a) existing `brief_before_interview_memory.json` pin still equal; (b) recompute `brief_hash` and `section_hashes` of the two real exported Briefs (copied
  to `tests/domain/fixtures/`) and compare with their stored `_hash`/`approved_baseline.section_hashes`; (c) empty structure leaves the hash unchanged and a non-empty one moves it;
  (d) memory and Postgres store round-trip of an old and a new Brief, and the dump of a Brief without structure has none of the four keys; (e) a session that was ever approved (`approved_version` set; `_apply_change` flips APPROVED back to BRIEF_REVIEW, so `turn.state` is the wrong test) is never given a first draft; (f) after a build, a second `_open_review` changes neither hash nor version (a digest-only change saves a version in `_commit` but `_open_review` computes the version from the hash only, which would leave an off-by-one version and block approval).

#### 3.3 Record shapes (values only; ids from `IdLedger`, tombstones on delete)
- Every record also carries a real (non-meta) field `decision: proposed | accepted` (like `AssumptionRecord.decision`): `_apply_record` refuses meta fields (`status`, `tier`), so Accept cannot be a field edit otherwise. Accepted or Locked records are PINNED on regeneration.
- `ModuleRecord(id MOD-###, name, purpose, apps[APP], features[FTR], roles[ROL], entry SCR|"")`
- `ScreenRecord(id SCR-###, name, purpose, module MOD, apps[APP], roles[ROL], serves[FTR], entities[{entity ENT, use view|create|edit}], pattern)`; `pattern` from a closed list in `catalog/structure_patterns.yaml` (list, detail, form, dashboard, auth, search, settings, ...). `use` makes access LOGICALLY checkable: a role on a screen that creates or edits an entity must have at least that access to it (see 5d).
- `FlowRecord(id FLW-###, name, goal, role ROL, steps[{screen SCR, action}], features[FTR], alternates[str], acceptance[str])`
- `EntityRecord(id ENT-###, key (ascii snake_case identifier), name (display, in the user's language), purpose, fields[{key (ascii snake_case), name, type, required, ref ENT, values}], states[str], access{ROL: none|view|create|edit|manage})`; `type` from a closed list in the patterns file (text, number, money, date, datetime, bool, enum, ref, image, file, location, list). Identifiers are ASCII so the React-writing AI gets stable names whatever language the interview used; display names follow the interview language.
- Role x screen/entity matrix, navigation graph (flow-step edges), phase and counts are DERIVED views (`engine/structure_derive.py`), never stored twice.
- Size: about 35 tokens per screen, so 60 screens + 12 modules + 25 flows + 30 entities is about 8-10K tokens (the Pune blueprint view today is about 7K). Slicing by module gives about 1-1.5K tokens per slice.

### 4. Size bands: how the tier is carried

- `catalog/size_bands.yaml` (data, hard rule 8). Band ids are `small | medium | large` (the page labels `large` "Enterprise"; the id must not be `enterprise` because `Mode == "enterprise"` already exists in the Brief and in `gate.py`): `small` (tier quick; screens 8-15, modules 2-4, flows 2-6, entities 3-8; module group size = all; review: summary), `medium` (standard; 20-30, 4-8, 5-12, 6-15; group 3; review: per-module, soft), `large` (thorough; 40-60+, 8-14, 10-25, 12-30; group 2; review: per-module, hard); `tier_to_band`; document thresholds (`medium` at >=25 verified claims, `large` at >=60; starting values, to calibrate on a live document batch); suggestion signals; the 1.25 over-band factor; the sufficiency thresholds of 5b (`screens_per_must_feature`, `module_screens_min`, `thin_factor`); the `research` block of 5c (depth, searches, gap-fill, max requests). Loader `catalog/size_bands.py` validated like `fact_kinds.py` (lazy, strict).
- Carried by: tier = `meta.plan.interview_budget` (existing, hashed once chosen). The band is DERIVED at draft time = max(tier band, document band, user override); stored hash-free in `meta.interview` (`size_band`, `size_source` tier|document|suggested|user, `size_target`, structure counts and issue count).
- Tier mismatch: (1) idea time: `suggest_band(situation.size_stakes, plan.depth, roles/apps in the hypothesis, named features)` runs after `situate`; if above the tier's band, ONE notice `size_suggestion` with a one-tap chip that sends the existing `budget_standard`/`budget_thorough` (never an automatic switch); (2) after the draft: counts above band max x1.25 -> notice + `structure_action set_band` ("Plan as Medium", regenerates from the same answers, no new questions; the band lives in hash-free `meta.interview`, so undo of a regeneration restores the records but not the band, by design); below the band: silent.
- Tier change mid-session: `set_budget` has no guard and `Room.of` is recomputed from the ledger on every call (verified in code), so the interview adapts at the next plan; the band is re-derived at the next draft and the outline digest changes, so only unconfirmed parts regenerate (confirmed items are pinned and passed as fixed). Already-shown `progress` stays stale (existing behaviour, noted).
- Document: the claims are already ledger facts (`origin="document"`, verified quotes). Document-derived `screen`/`flow`/`entity` facts become must-include seeds for the outline call (provenance `document`, Locked-eligible); the raw document text never reaches the new calls.
- "Decide the rest": unchanged flow; the draft is built from the ledger plus assumptions; every item is Default/assumed; Approve All bulk-confirms (status `confirmed`, tier stays Default).

### 5. Generation design (gateway calls, parallel, digest-gated)

Three new calls (two writers below plus the findings-only critic `cmp.review_structure` of 5d), all route `standard`; the two writers are `lane="writer"` (concurrency 8, rpm 120; per-attempt timeout is capped at 60 s by the gateway), effort low, no tools, all free-text inputs in `untrusted_inputs`. Folder pattern as `cmp.decide_answers`: `spec.py, schema.py, system.jinja, user.jinja, validate.py, fallback.py, mock.py, adapter.py, examples/{en,hi,hinglish}.json`; port in `engine/ports.py`, `calls/registry.PORT_BY_CALL`, `CALL_PROFILES` row, row in `docs/prompts/compass-calls.md`.

1. `cmp.draft_outline` v1 (max out 3000, 45 s). In: language, band numbers, project card, features/roles/apps (ids, names, priority), fact digest (<= 4500 tokens), seeds (document or user `screen/flow/entity` facts), pinned confirmed items, optional instruction. Out, deliberately SHORT (about 0.5K tokens small, 1K medium, 2K enterprise): `modules[{ref,name,purpose,apps,features,roles,screen_target}]`, `entities[{ref,name,purpose,owner_module}]` (names only: field detail would make this serial call about 3.5K tokens at enterprise size), `journeys[{ref,name,role,legs[module ref, in order, a module may repeat],goal,owner_module}]`. The shared vocabulary (modules, entity names, journey list) is frozen here so module calls can run in parallel.
2. `cmp.draft_module` v1 (max out 3000, 45 s). One call per MODULE GROUP (`group_size` from the band: small = one call for all modules, medium = 3, enterprise = 2). In: the group's outline modules WITH THEIR EXISTING IDS (so records match by id first, name second, as `_sync_list` does; a user rename or a reworded model name must not mint a new id), the whole entity vocabulary (ids, names, purposes), roles, apps, the features they deliver, journeys that touch them, a fact slice, pinned items, optional `instruction` (user regenerate text) and `issues` (repair). Out per module: `screens[{ref,name,purpose,pattern,apps,roles,serves,entities}]`, `segments[{journey,leg,steps[{screen,action}]}]`; per group: `entities[...]` with fields/states/access for the entities its modules OWN (so field detail is written in the parallel wave), and, for journeys it owns, `acceptance` and `alternates`.
   Cross-module flows are assembled IN CODE by concatenating the segments in leg order (a journey that revisits a module has one segment per leg; no extra serial call). A journey with a missing leg is dropped with a warning.

Code after the calls (`engine/structure_draft.py`, `StructureController`, same shape as `interview_compile.compile_ledger`): resolve refs, allocate ids (match by id first, then name; tombstone the rest), merge pinned items (accepted or Locked records survive a regeneration), derive, run `structure_checks`, DETERMINISTIC fixes (drop dangling refs, dedupe, attach an unused entity to its owner module's entry screen, drop a flow with fewer than 2 steps with a warning: a module call cannot create entities, so these cannot be left to a module repair), ONE repair round (`draft_module` with `issues` for the failing modules only; serial, so it is a third stage and is in the latency table), then record what is left as assumptions with a NEW basis `structure` (not `review`: `flag_review` tombstones undecided `review` rows) and `meta.interview.structure_issues`.
  Digests in `meta.compile_digests` (`structure:outline`, `structure:module:<id>`; `stale_keys` only prunes `fill:` keys, so `structure:*` is pruned by the controller). A digest covers MACHINE INPUTS ONLY: for a module, its own outline entry, its features (ids, names), its roles, the entity names it references, the band, the language; never pins, status, `decision` or an instruction (otherwise Accept or an undo would trigger a regeneration of the module the user just reviewed, and a probe assume-fix on one role would redraft everything). An explicit `regenerate_module` stores the same machine-input digest, so the next build-time run does not redraft it. Digests are written in the same turn as the content, and a re-run with the same inputs is an exact no-op (zero calls, same hash, same version).
  A failed call is the deterministic floor for ITS group only, flagged and counted in `meta.interview.fallback_count` (a failure in live batches; 14 scenario files assert `fallback_count: 0`, so the mock handler must never count a fallback).
  Referential integrity: ids are stable (a rename keeps the id), but removing a feature, role or app tombstones it and leaves dangling `serves`/`roles`/`access`/`apps`; `structure_checks` also runs at `_open_review` and prunes dangling refs deterministically (reported in a notice), and `validate._reference_problems` learns the new refs.
  Pivot or an answer edit that changes the idea: pinned records stay only while the features they serve still exist; a pivot clears the structure (pins released), since `lock_guard` covers slots only.

- Deterministic floor and mock handler (data-driven, nothing company-specific): `catalog/structure_patterns.yaml` maps feature `family` (from `families.yaml`) to module and screen templates plus a generic list/detail/form set; mock scales screens per module to the band target; names come from the Brief's own feature and role names. Both always pass the structure checks.
- Consistency checks (`engine/structure_checks.py`, pure, severities in data): ERROR (repair, then review assumption): screen without or with unknown module; module without screens; unknown role/app/entity/feature/screen refs; flow with <2 steps or an unknown role; entity not used by any screen; entity access for an unknown role; in-scope feature without a screen; `must` feature without a flow that has acceptance; role with no screen and no entity access; app with no screens. WARN: screen in no flow and not an entry; module with 1 screen or over 12; counts outside the band. The checks are wired into the build (after the draft) and into Gate 1 (blocker count), which today has no such check.
- Wiring (verified in `Service._advance`, SEEDING branch): after `_compile_brief`, the existing `asyncio.gather(self._seed(turn), review_mod.scan_findings(self, turn))` gains a third task `self.structure.compute(turn)` (`return_exceptions=True` semantics: a failed branch must not leave the others running; `compute` catches its own errors and returns the floor). Seed (about 15 s) and scan (12-20 s) already run there, so the structure step only adds the part of its time that exceeds them. `compute` SNAPSHOTS the inputs it needs when it starts and then only awaits model calls; it returns a `StructureResult`; `structure.apply(turn, result)` runs after the gather and MUTATES `turn.brief` in place (never reassigns it), because `_seed` calls `_rebuild(turn)` (which replaces `turn.brief`) and any write made on the old object is lost; it must not call `_rebuild`/`merge_derived` itself. The same step also runs, sequentially and digest-gated, inside `_open_review` -> `_compile_brief` (reached after probes, which may change slots, and after answer edits in review): usually a no-op, and a probe fix redrafts only the module whose slice changed. Skipped when `session.approved_version` is set and no structure exists (never give a first draft to a session that was ever approved; when one exists, only the deterministic prune runs), when the engine is `legacy`, or when the switch is off.
- Switch (verified: scenario YAML `policy:` overrides `InterviewPolicy` fields only; about 15 test modules call `build_service` with `DEFAULT_CONFIG`, bypassing `engine_config`; `compose.build_service` picks a product policy only in live mode): the switches are two fields ON `InterviewPolicy`, `structure_enabled` (default False) and `structure_prefetch` (default False). So every existing test and scenario keeps today's behaviour, scenarios can opt in with `policy: {structure_enabled: true}`, and `engine_config`'s `base` dict names it explicitly. `PRODUCT_INTERVIEW_POLICY` sets `structure_enabled=True` (live product runs: `compose.build_service` live branch, `live_batches.planner_config`, `smoke_config` are the three places that choose a policy), and `COMPASS_STRUCTURE=on|off` overrides it in `resolve_config` (same pattern as `COMPASS_INTERVIEW_ENGINE`) for mock runs and the owner's browser. Scenario fixtures are NOT strict for unlisted calls (`unscripted` defaults to mock; only `unscripted: fail` and a bare `ScriptedGateway` fail), but the flag keeps their call counts and hashes unchanged. New structure tests and scenarios (SB-ST-*) enable it explicitly. Other tunables (group sizes, caps) are data in `size_bands.yaml`, so there is no new policy dataclass. Pins that must stay green untouched: `test_brief_interview_memory.py` (hash pins), `test_domain.py:55`, `test_handoff_order.py`.
- Digest keys are STRUCTURAL inputs (see above), not the whole ledger: otherwise every closing answer would invalidate the digest and any prefetch.
User approval and edits (Gate 1): modules are rows of a new Brief-view section `structure` (so the existing Accept, assumed-ratio, high-impact confirm and Approve All logic apply to them unchanged); deep browsing and editing live in a Structure tab. Edits (verified in `patch.py` and `service.py`): `_on_brief_edit` builds exactly ONE `set` PatchOp, and `_apply_change` can run once per turn (the change id comes from the stored count and only `turn.change_set` is saved). So: rename, change a field, move a screen (`set screens.SCR-004.module`) use the EXISTING `brief_edit` event and path grammar (ChangeSet, undo, voided sections, history; the edit stamps `user_text` evidence, so the record becomes Locked-eligible and pinned). Everything else is a new inbound event `structure_action {action: accept | add | remove | regenerate | set_band, section, target, text, band}`, handled as ONE multi-op ChangeSet in ONE `_apply_change` call: `add` (a record, id from the ledger), `remove` (a module with its screens, the flow steps that pointed at them and its `entry`, cascaded in the same ChangeSet), `accept` (sets the real `decision` field and does NOT create Locked: it must not carry user evidence), `regenerate` (one `draft_module` call, the user's text as untrusted `instruction`, accepted and Locked records pinned) and `set_band`. Engine-driven writes need an actor: `_apply_change` passes none today and the default is `user_text`, so a regenerated draft would be stamped confirmed and Locked; add an `actor="engine"` parameter (provenance `model_knowledge`, tier Default, decision proposed). `ChangeSource` gains `"structure"` (no DB constraint on it; verified). Approve All: `_on_approve_all` builds ops only for pending assumptions and recomputes blockers once; it must add the structure `accept` ops to the SAME change set, or the blocker below survives. New blocker `structure_unreviewed` (added in `Service._blockers`, string `blocker.structure_unreviewed` in en and hi) by band review mode: small = none (shown, one summary row), medium = soft (notice only), large = hard (every module accepted, or Approve All) - this mirrors doc 03's G1.5 profile.

### 5b. Sufficiency for large apps (owner requirement after plan review: richer answers must give a Brief that is enough for 50-60 screens)

Rule: the more the person (or the company) tells us, the more of it must END UP in the structure, and a large app must not come out thin. Code enforces it; it never pads.
- Nothing the person said is dropped by a size cap: the outline gets a compact digest (<= 4500 tokens), but EVERY active fact of the detail kinds (`screen`, `flow`, `entity`, `rule`, `number`, `acceptance`, `compliance`, `integration_detail`, `nfr`) is routed to at least one module slice by its `refs` and topics (each slice <= 1500 tokens), so 100+ facts from a 25-30 question interview or a document reach the module calls even though one call could not hold them. Enterprise-mode answers (the `org.*` slots: identity/SSO, approvers, regions, data classification, API catalog) are passed to the outline as `org` context, so modules such as Admin, Identity and Audit are drafted when the company said they exist.
- New checks (data-driven thresholds in `size_bands.yaml`, per band): `feature_thin` (an in-scope `must` feature served by fewer screens than `screens_per_must_feature`: small 1, medium 2, large 3), `module_thin` (a module below `module_screens_min`: large 3), `fact_orphan` (a detail fact that no module slice contains). These three TRIGGER expansion. `thin_draft` (total screens below `thin_factor` x the band minimum, 0.8) is a WARNING ONLY and never triggers expansion: a simple app in a large tier must stay small, because the band is guidance, not a quota (2.1.2).
- ONE expansion pass, in the same serial stage as the repair round: the failing modules are re-sent to `cmp.draft_module` with machine-written `issues` naming the thin features and orphan facts ("cover these features and facts in more depth"); the model adds screens, flows and entity fields; code merges and re-checks. Whatever is still thin afterwards is shown (notice, `structure_issues`, an assumption with basis `structure`), never padded and never blocking.
- Large-band depth per record is the same schema as small (decision 2.1.1); what grows is the count and the traceability (`serves`, `entities`, flow `acceptance`, entity `access` per role), all checked.
- Acceptance test for this requirement (mock, offline): a large-tier session with a document fixture of 60+ claims and 4+ roles/2+ apps produces a structure inside the large band (40-60+ screens), every in-scope `must` feature has >= 3 screens and a flow with acceptance, every role has access, no detail fact is orphaned, and `module_slice` of each module fits the 1.5K-token budget.

### 5d. Logical correctness and realism of the final Brief (owner requirement: whatever the person said, the Brief must be correct and realistic)

Three layers, cheapest first. Layers 1 and 2 are code and data; only layer 3 is a model call, and it can only REPORT.
1. Logical checks in code (`structure_checks.py`, severity in data; errors are fixed deterministically or by the repair pass):
   - Access logic: every flow's role can open every screen of the flow (`flow_role_cannot_access_step`); a role on a screen that creates or edits an entity has at least that access to the entity (`screen_entity_access_conflict`: "a patient may view lab reports, never edit them"); every role has a home screen (entry, dashboard or list) in its app (`role_without_home`); a screen's apps are inside its module's apps; every app has an entry and an auth path when `access.auth_methods` is set.
   - Scope logic: a screen serving only `out` or `unsupported`/`needs-engineering` features (capability tier C: games, AR and the like) is an error (`screen_for_excluded_feature`); screens serving only `later` features are kept and derived as phase later; a user-pinned item that conflicts with an exclusion is shown, never silently dropped.
   - Data logic: no entity without fields or without a key; `ref` fields point at existing entities; money-like fields (price, fee, amount, total) must be typed `money`, dates `date`/`datetime` (`field_type_implausible`); near-duplicate screen names inside a module (`screen_near_duplicate`); the same name in two modules is fine.
   - Facts logic: a numeric rule or number fact (for example "delivery within 5 km") that names an entity or screen must be present in that module's slice (`fact_orphan`); the checker never edits a number.
2. Realism rules from data (`catalog/structure_rules.yaml`, no company or app type named in code; each rule = a condition over slots or facts and a required capability): sensitive data `health`/`finance`/`children` -> consent and privacy screens, role-restricted record access and an audit trail; a `payments` integration -> checkout, payment methods, receipts and refunds; `phone_otp` auth -> verify-code screen and resend rule; more than one locale -> language setting; more than one role -> role-gated access in every module; delivery or tracking features -> status screens per role; admin-like role -> user and role management. A rule that is not satisfied becomes a finding for the repair pass (never an invented fact); each finding names the rule id and the slot or fact that triggered it. The rule pack is a starting set, reviewed in the live runs below.
3. Semantic critic `cmp.review_structure` v1 (lane `critic`, standard route, effort low, max out 1500, 45 s; medium and large bands only, `critic: true` in `size_bands.yaml`; findings only, in the style of `cmp.scan_ambiguity`, so it can never change a value): input = the structure outline (ids, names, roles, serves, entities), the active facts of the detail kinds and the roles' `rough_permissions`; output = findings `{code: contradiction | unrealistic | missing | inconsistent_permission, ids[], fact_id, note}`. Code drops any finding that does not cite a real id and a real fact (no free-floating opinions), then turns the rest into repair `issues`. It runs right after the module wave, in parallel with the deterministic checks, so it adds one call of about 8-12 s only when it runs.
4. Provenance guard for structure (like `lock_guard` for slots): a Locked or seeded record whose cited facts were superseded or are no longer verified is downgraded to Default and set back to `proposed`, so a correction by the person ("no admin app after all") can never leave a stale Locked screen.
- Pipeline order: draft (outline, module wave) -> deterministic fixes -> [checks ‖ critic] -> ONE repair-and-expansion pass for what is left -> final checks -> assumptions/notices for the remainder. Nothing here blocks Gate 1 except the band's review mode (5, `structure_unreviewed`); unresolved findings are listed to the person, in plain words, with the fact that caused them.

### 5e. Interview optimization for medium and large tiers (the answers must be the kind that decide structure)

- The planner is told the answers will be turned into a screen-by-screen breakdown. `cmp.plan_questions` (v4 -> v5) gets an additive optional input `structure_focus` (set only when `structure_enabled` and the band is medium or large; the prompt block is short): prefer questions whose answers decide screens, who can do what, the flows, the data the app keeps, approvals and escalations, numbers and limits, named outside systems and reports; do NOT ask what the draft can propose and the person can approve later (module lists, screen lists, entity lists); one question per decision. Tier numbers, Room, validators and the necessity rule are unchanged. A flag-off request renders exactly as before (prompt test).
- The closing question for a large app lists the person's modules and features (already built from the ledger) so the must-have picks map onto structure.
- Facts are typed so they route: the existing compile typing (`kind`, `refs`) is re-checked in live runs for screen, flow, entity, rule, number, acceptance and compliance kinds; a kind that stays `other` but names a role plus an action is listed in the live review as a calibration finding.
- Large-tier answers from a company (org slots, documents) are never re-asked: document claims already close their needs (D-104) and the structure reads them as seeds.

### 5c. Research guidance in the Brief (owner requirement: the Brief tells research what kind of app this is and how deep to go)
