Mobile Design Engine Atlas

You bring an idea or a PRD. Four agents turn it into one approved spec: one interviews you, one researches in front of you, one writes the spec, and one checks and packages it. Small models build a live preview in parallel. You approve once, and the backend is built to match what you approved.

The whole platform on one page

Four engines run in a fixed order under one orchestrator. You approve at three mandatory points. After the third one, everything runs by itself.

Program Orchestrator
Keeps order. It runs one engine after another, remembers every version, holds your approvals and the audit trail, and turns change requests into controlled edits.
Context Engine
Turns conversation and documents into one verified spec. You approve twice here: the Brief (G1) and the Spec (G2).
Spec Package
The single source of truth: one readable file, plus small slices, design tokens, an API contract, test journeys and a build plan.
Front-end Engine
Small models build the app in parallel from slices, using mock data, and host a live preview you can click through.
G3: the last gate
You judge look and behavior on the live preview. Nothing after this needs you, apart from optional sign-off.
Approved Build Manifest
A frozen record of what you approved: rules in plain words, the API contract, sample data and the journeys you walked through.
Backend Engine
Builds the server from that record. It is accepted only if the API matches the contract and the approved journeys replay with the same results.
QA Engine
Replays the journeys, checks store readiness and writes the release report.
Shared services
One gateway for every model call, storage for files and the spec graph, a registry of modules and kits, document reading, search, preview hosting and the test harness.

The Context Engine: four agents, one file each

Each agent reads only what it needs, mixes model calls with plain code, and writes one file for the next. Research runs in front of you right after you approve the Brief, with live progress and a Skip button. Select an agent to see exactly what it does.

One spec, kept as a graph, served in small slices

Every agent writes into one connected graph, and the Spec agent commits it in one place. Every file the other engines use is generated from it, so nothing can drift apart. Workers never read the whole spec; they get a small slice.

Locked, Default, Open
Locked means you or a document said it, so builders must follow it. Default is our recommendation, which a builder may change if it records why. Open is left to the builder. This stops us from binding the designer and stops models from inventing requirements.
Sources on everything
Each item says where it came from: you said it, your PRD page 4, assumed (and why), researched (with a link), or a pattern default. Research and assumptions can never become Locked.
Stable IDs
An ID such as SCR-021 is never reused, even after deletion. That keeps a hundred rounds of change, regeneration and traceability from tangling.
Spec Server
A read-only service that hands out slices over a standard protocol (MCP) and an AGENTS.md entry file, so any coding agent can use the same spec.

How we know a weak model can build from the spec

Before you see the plan, the spec passes three independent checks. They run while the spec is written, not only at the end, so problems are found before the expensive screen batches. The key one tests the spec against the same kind of model that will build from it: if that model has to ask a question, the spec is not finished.

Why not just ask a smarter model?
2026 research found that stronger code models are not reliably better at noticing what is missing, and that they ask too few questions when several things are unclear. So we use structure and a weak tester, not "think harder".
Why a different vendor for the critic?
Two models from one family tend to share blind spots. Writer and critic come from different vendors, so their mistakes are less likely to match.
What you see
Anything the probe had to assume appears under "We assumed" at the Spec gate, each with a toggle. Parts that could not be fixed cleanly are flagged "degraded", never hidden.
Benchmark
A private test set (SpecBench-Mobile: 15 kinds of app, with and without a PRD, plus tricky and multi-language cases) scores every change to prompts or models. Any broken rule is an automatic fail.
The 14 things a front-end builder must find in the package (builder needs, BN-01 to BN-14)

If the only input were "build a mobile app", the builder would have to ask these. The chain exists so that none of them reaches the builder unanswered. Verify marks each one satisfied, defaulted, degraded or missing. A missing one blocks the approval of the spec (G2).

Build in parallel without collisions

The spec ships with a build plan: small tasks, each owning its own files, run in waves. Because the plan is made before any code is written, workers cannot step on each other.

Which model builds which task

Easy (S)
Small model, quick. Simple lists, detail pages, static screens.
Medium (M)
Small model at high effort, or a mid-size model. Forms, dashboards, screens with several states.
Hard (L)
Mid-size or large model. Many states, custom components, rich animation or several integrations.
If a task fails twice
It moves up one class automatically, and the scoring rule is flagged for review.

Each task gets a difficulty score from the spec (sections, states, side-effect actions, custom components, integrations, gestures). The Context Engine recommends; the front-end engine decides. A worker usually sees under 20k tokens.

Task card
The unit of work. It names what the task depends on, which files it alone may write, what it reads, which checks it must pass, how hard it is, and when to escalate.
Interface freeze
After the foundation, the shared contracts are published once. A worker that needs a change must file an interface-change request, which re-queues only the tasks that depend on it.
Why this beats fixing conflicts later
Other tools merge parallel work afterward and use extra agents to resolve conflicts. Here the plan prevents the conflicts. A large public experiment that split work between strong planners and cheap workers cut merge conflicts from roughly 70,000 to under 1,000.
Honest limit
Models still miss on the hardest screens and on native features. Those are flagged ahead of time (tier B) and listed as hand-off tasks instead of being promised.

You approve once on a live preview, then the backend follows

The preview is not a screenshot. It is the real app on mock data, with controls that let a non-technical person check design, behavior and features. The journeys you walk through become the backend's exam.

Web link first
The default preview is a web link anyone can open. Expo Go is used only when its version matches (the App Store copy lagged new releases in May 2026). Native-only features are shown as "simulated" with a badge.
Click any element
Generated files carry spec stamps, so a click shows the spec item, who said it or what it was based on, and a "change this" button.
Behavior Book
Business rules in plain words. Anything the mock simply hard-coded, or the PRD never said, is listed under "confirm" and must be answered before you approve.
Integration checklist
For each pretend integration (payments, SMS, maps, push) we recommend a provider. "Use recommended" is the default, and test keys are enough to finish. Real keys can come later and never block delivery.
After approval
Your preview stays live. Later changes become small release deltas: the contract diff, then the backend change, then the journeys re-run.
Never a store app that runs generated code
Apple enforced its rule against downloading app-changing code on several AI builders in 2026. Our deliverables are ordinary Expo projects built the normal way.

Every change goes through the spec

You can ask for a hundred changes. Each one is turned into exact edits, sorted by how big it is, checked on a copy, shown to you if it is big, applied, and can be undone.

Six lanes, from tiny to foundational

L0 Explain
"Why is this here?"
Answered from the source of each item. Nothing changes.
L1 Cosmetic
Colors, type, wording, icons, spacing, theme
Applied right away with an undo button. One edit to tokens or copy, even if it touches every screen. Target: spec edit within about 10 seconds.
L2 Local behavior
Add a field, a validation, a filter, an empty-state message
Applied right away with undo. Only the affected screens are rebuilt, and API changes are additive only. Target: about a minute.
L3 Structural
A new screen, role, entity, flow or report
You confirm after seeing the impact. Affected sections need approval again. Target: a few minutes.
L4 Scope boundary
Anything marked Later, Out or Unsupported, a Locked item, or a hard native feature
Scope Change Protocol card with options. Unsupported things cannot be added, only replaced by an alternative or listed for engineers.
L5 Foundational
Add an app, change the login model, change the kind of product
A new program version. The Spec gate (G2) reopens and the pipeline restarts from the Blueprint.

Latency targets are initial goals (the architect's judgment), not measurements yet.

Scope ledger
Every feature is marked in, later, out, unsupported or needs-engineering. You can flip it in checklists at any gate and in the preview. This is also where "make it like [other app]" lands: a reference list you toggle.
Variants
Vague requests ("make it more modern") return three concrete options instead of a guess. A look can be forked, compared side by side, then merged or dropped.
Many changes at once
Rapid-fire or dictated lists are split into numbered requests and read back to you in one tap-to-confirm list. They are batched into change sets, each reversible.
Hand-edited code
If a developer edits generated files, they are locked and skipped on regeneration. A later change that touches them produces a conflict card instead of overwriting.

Apps are composed from modules, not templated by category

The stack is fixed (Expo, React Native, TypeScript). The kind of app is not. The engine selects, adapts and extends capability modules, so a food app and a banking-style app use the same machinery.

Why modules
A module carries proven screens, data, rules and states. Composing them gives consistent quality across many kinds of app and leaves less for a model to invent.
Honest tiers
A reliable login, lists, forms, dashboards, checkout screens. B flagged real push, live tracking, payments SDKs, camera, offline sync. C hand-off custom native wrappers, on-device ML, live collaborative editing.
A Zomato-class program
We deliver the customer, restaurant, rider and admin app shells with flows and mock data (on the order of 60 to 120 screens), then a verified backend for the approved behavior. Live tracking and recommendations are listed as hand-off work, not promised.

Every model call follows the same safe path

All model calls go through one gateway. Output is checked, repaired once, and falls back to a safe default, so one bad answer never silently reaches the next stage.

Cost is not the constraint
Estimated model cost for the whole Context Engine on a 100-screen, two-app program is roughly $0.5 to $2 before retries (an estimate). The expensive parts are building and hosting, which is why the spec exists: to reduce rework there.
Two vendors
Anthropic and OpenAI models can both do any job. If one is down or slow, the same call runs on the other. This also lets us choose a better or cheaper model later by passing the test set, not by rewriting the product.
Pinned and tested
Models are pinned by name. Switching one needs a full benchmark run, equal or better results on every gate, a trial on part of the traffic, and a way back.
Plain baseline safety
Secrets are removed before text reaches a model, documents and web pages are treated as data and never as instructions, mock data is synthetic, and previews use expiring links. Deeper compliance work is deliberately deferred.

    The order we build in, one agent at a time

    Each step has one prompt for the builder, one test gate, and your sign-off before the next. Gate numbers are initial targets, not measurements.

    1. NOWResearch agent: design review (v3)Doc 13 v3 and its build prompt are ready. You review them, then give the go for the build and the bake-off.
    2. STEP 0Audit the repoRead-only. Gate: a reuse map of what exists versus this design. Folded into the Compass prompt's Phase 0.
    3. STEP 1BackboneSpec graph v3, validator framework, schema registry, invariants. Gate: invariants pass; the same graph renders the same file.
    4. STEP 2Gateway and test harnessSecond vendor and failover; search port for Research; benchmark skeleton. Gate: both vendors behave identically.
    5. STEP 3Discovery (Compass)Built; hardening continues. Gate: the Brief checks pass on real interviews; 90%+ of PRD requirements captured; no unevidenced Locked items.
    6. STEP 4Research agentForeground run after G1, depth chosen from what you said, parallel workers per topic, entity-anchored queries, quote-verified typed facts indexed by your feature, role and data ids. Gate: every high-impact claim sourced, quoted and dated; zero generic queries; fails softly (doc 13 §14).
    7. STEP 5Spec: Product laneModule library (first ~20 modules) and Contract v0. Gate: validators pass; screens mostly from proven modules.
    8. STEP 6Spec: Design laneTokens and composition rules. Gate: contrast always passes; three looks genuinely differ.
    9. STEP 7Spec: Screens lane, join and FreezeParallel screen batches after Freeze. Gate: all required states present; every reference resolves.
    10. STEP 8Verify and packageStreams while Spec writes; builder-needs coverage (BN-01 to BN-14). Gate: weak-model test passes on 85%+ of sampled screens; no need is missing.
    11. STEP 9Programs, changes, viewsMulti-app, change lanes, review screens. Gate: lane sorting 95%+ correct; undo exact.
    12. STEP 10Design the Front-end EnginePreview hosting, agent choice, model routing. Then Backend and QA design.

    The order follows doc 09 §2 and doc 12 §10. The Spec agent is built in three phases that share one orchestrator (steps 5 to 7).

    Why this can become a company

    The product sold is predictable delivery: approve the experience on a live preview, and the matching backend is built and proven against the same journeys. Figures below are press-reported or the architect's judgment; check sources before using them with investors.

    Who pays
    IT-services firms and agencies (beachhead, India first) face AI-driven price pressure and need faster discovery and delivery. Enterprise digital teams in the US, EU and India want predictability and code they own. Founders are top of funnel.
    What it replaces
    A custom enterprise mobile app is commonly quoted at roughly $100k to $500k in agency blogs. A per-program price of $5k to $50k plus a platform fee is a hypothesis to test in pilots.
    Sold alone first
    The Context Engine can be sold by itself (requirements, wireframes, API contract, BRD/SRS in hours), which earns revenue and data before the other engines mature.
    Not differentiators
    Single sign-on, SOC 2 and private hosting (Replit already has them), parallel agents, and "has a planning step". Every serious competitor is adding these.

    Terms used above

    Brief
    The first file: what you are building, for whom, the features, the look, the login, and what we assumed. You approve it at G1.
    Agent
    One of the four units of the Context Engine: Compass, Research, Spec, and Verify and package. Each writes one file.
    Lane
    A group of steps inside one agent that runs beside another lane. Spec has three: Product, Design and Screens.
    Freeze
    The point in Spec where the shared decisions (roles, data, operations, navigation, tokens) become read-only for the Screens lane.
    Builder needs (BN-01 to BN-14)
    The fourteen things a front-end builder must find in the package. Each is satisfied, defaulted, degraded or missing; missing blocks G2.
    Visible research
    Research runs in front of you right after you approve the Brief: only what the model cannot know is searched, with live progress, a time box and a Skip button.
    Spec graph
    The connected set of items (screens, features, data, rules, roles) that is the single source of truth.
    Slice
    A small, budgeted piece of the spec given to one worker: shared rules plus one screen.
    Contract v0 / v1
    The API shape (what the app asks the server and what comes back). v0 comes with the spec; v1 is frozen at G3 after checking what the app really calls.
    Golden journey
    A scripted walkthrough of an approved flow, with the expected result at each step. Used in the preview, then as the backend's test.
    Behavior Book
    The rules the backend will follow, written in plain language, with anything unconfirmed listed for you to answer.
    Canary model
    The deliberately weak model that tests whether a slice is clear enough to build from.
    Tier A, B, C
    How reliably we can build a capability: reliable, supported with a flag, or handed to engineers.
    Change set
    A group of exact spec edits made for one request, with its size, impact, approvals and an undo.
    Wave
    A phase of the build (W0 to W7). Tasks in the same wave can run at the same time. Research is a different thing: one visible run of the Research agent.
    Module
    A reusable block of screens, data and rules, such as "cart and checkout" or "appointments".
    Degraded
    A flag for an item the system could not fix cleanly. It is shown to you, never hidden.
