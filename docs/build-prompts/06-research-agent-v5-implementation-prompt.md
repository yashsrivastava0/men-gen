## 1a. Detail: how the result gets richer, and stays rich (binding)
The owner's goal: Spec gets **enough, and a little more**: specific, sourced, structured detail in every area it decides, so it does not guess or reason again. **Detail comes only from what pages state; grounding (RC-3) removes invented detail, never true detail.**
- **D1 Extract everything the page supports.** The extraction instruction stays: return as many **distinct, specific, useful** items as the page really supports; prefer concrete structure over summaries (every feature a product lists, every screen section and state, every field the page names, every step and exception, every provider capability, limit, fee, number and date). RC-3 only adds "only what the passage states". Test: a fixture page with N true facts yields at least 0.9 N items (with the test double) and no invented attribute.
- **D2 Read more of good pages.** Yield-adaptive reading: when the first extraction from a page returns items from most of its passage windows, extract the remaining windows too, up to `max_windows_per_page` (data, default 6 [J]; official, documentation and help pages first). No new searches, a few more calls. Report how many pages got extra windows and what that added.
- **D3 Detail lives in `data`.** One item per thing; its fields, states, steps, numbers and conditions go in the typed `data`, not in long claims.
- **D4 Nothing kept is lost.** RC-1: a main store plus an appendix, every main-store item in its lane slice, digests only as an index, the report lists everything.
- **D5 Depth by size (what Spec should get; the counts are [J] expectations to report against, never caps).** Small: a pattern sheet (the usual features with how common each is, 8 to 12 typical screens and one navigation pattern, the main entity's fields and states, 3 to 5 provider facts, platform guidelines and accessibility, formats and sample-data hints; about 80 to 150 verified atoms before merging). Medium: adds a competitor comparison (4 to 6), journeys with exceptions, entity patterns and lifecycles, provider options with limits and fees, a rules list (about 180 to 300 atoms). Big: adds playbooks per module group (up to 8), notes per external system, role-by-role exceptions, a compliance list, realistic data per entity, design trends (about 400 to 650 atoms). If a run returns far fewer than expected, investigate extraction, reading and queries before anything else.
- **D6 The quality bar (apply it to every recorded or live output you can read).** Read it as Spec's lanes would, and fix the planner, slot schemas, prompts, reading or assembly until: **blueprint** can list the usual features with how common each is, typical screens and navigation, journeys with steps and exceptions, entities with fields, allowed values, validations and states, and rules with numbers; **integrations** can compare providers on auth, events, sandbox, limits and fees; **design** has platform guidelines, accessibility and script needs (plus conventions when a page states them); **screens** can list sections, components, actions, states and validations; **mock** has formats and realistic data; the `confirm` list is present. Report a blunt assessment with examples.
- **D7 Depth meter.** In the Quality tab and in the report, show per job the slots filled over required, the items by kind and the items with typed data, and per lane the count against the D5 expectation for the class (green, amber, red), so the owner sees at once whether the result is detailed enough.
- **D8 No padding.** Thin areas are shown as gaps; never fill them with generic filler (R27, light mode).
- **D9 Stop by yield, not by count (cap 1).** A topic stops when its required slots are filled, ideally from at least 3 independent sources for high-impact slots; the whole run also stops when the last N searches (data, default 6 [J]) found no new normalized key. The ceilings stay only as a runaway guard. Keep the built 10% round-gain rule.
- **D10 What Research covers and what it does not.** Research brings external, regional and current facts only: what is normal for this kind of app, providers, limits and fees, rules with numbers, local formats and sample data, stated design conventions. **Universal behaviour** (sign-in, error and empty states, permissions matrix, API shapes, background jobs, notifications) belongs to Spec's own module library: do not search for it or pad the output with it.
- **D11 Assembly is code.** No model call emits the whole file or hundreds of records; code builds items, norms, slices and the report, and a model only writes short optional notes in small batches. The Spec-side packs and the bundling of `APP_SPEC.md` are Spec's job (not in this task); you only guarantee the fields they need (`tokens_est`, `rank`, `applies_to`, `store`, the compact view).

## 6. Part A: the standalone app (back end)

### 6.1 Live-only composition, no mock logic
- `python -m mde_research_agent` (no flags needed) starts **one process, one port (default `127.0.0.1:8120`), same origin**: the API **and** the static front end. Options: `--host` (default 127.0.0.1), `--port`, `--inputs <dir>`, `--data <dir>`.
- **Remove from the app's runtime path:** `--memory`, the in-memory store, mock model handlers, the fake search and fetch ports, the "MOCK MODE" banner, any replay mode. **Move test doubles into the test tree** (`tests/support/`; if `fakes.py` and `testing.py` live in `src/`, move them and fix imports). The app's composition root must be **unable** to select a double. If the gateway's `CallSpec` contract forces a mock handler to exist inside the spec, keep the attribute but guard the composition: the app always runs live and never selects the mock handler.
- If a provider key is missing, the app **still starts** (so the front end can explain) but every start-run action returns a plain refusal naming exactly what to set (`TAVILY_API_KEY`, `SERPER_API_KEY`; booleans only, never values). **Never fall back to canned content.**
- **Deterministic fallbacks** (deterministic query variants, default use notes, `unchecked`) are real degraded paths, not model mocks. Keep them only where they cannot invent facts, flag every use as `fallback`, count it, show it in the run view and the report. Extraction has no fallback: a failed extraction yields no items.
- **Recording is always on in the app:** every run writes its search results, pages and model calls as compressed cassettes under its run folder (developer scripts can replay them; the app cannot).

### 6.2 Store and data folder
- Data folder `RESEARCH_DATA_DIR` (default `agents/research/.runtime/`, git-ignored): `runs/<run_id>/` (`research.json`, `evidence.json.gz`, `events.jsonl`, `input.json.gz`, `cassettes/`), `spend-record.json`, `uploads/`, `spot-checks/`, `settings.json`, `logs/`.
- Add a **file-backed store** behind the existing store interface (atomic writes, append-only events, a lock for a single process, the same recovery behavior as PostgreSQL). It must pass the **same shared store contract suite** as the memory and PostgreSQL stores. PostgreSQL stays the production store (selected by configuration); **the app never uses the in-memory store.**
- Persist across restarts; a run cut off by a restart becomes `interrupted` **with a terminal event** and keeps the spend so far.

### 6.3 Inputs discovery and preview (zero cost)
- `RESEARCH_INPUTS_DIR` (default `<repo>/docs/compass/research-inputs`, **read-only for the app**; never write there). Scan `*.json` to depth 2 on every list request, cached by (path, size, mtime). Identity is the SHA-256 of the file bytes (first 12 hex); the API maps an id to a path internally, **never accepts a path from the client**; refuse symlinks that leave the folder; skip non-UTF-8 and files over 25 MB with a reason.
- A valid input is a Compass **format-2 export** whose `approved_baseline.hash`, `brief._hash` and `export.brief_hash` agree (RV-13). Otherwise list it under **skipped files** with a plain reason (`not_json`, `not_a_compass_export`, `format_not_supported`, `hash_mismatch`, `not_approved`, `too_large`, `unreadable`). Same content under two names lists once.
- **Preview** for each valid input, computed by the real intake, load, signals and the **deterministic** planner, **no model call, no web call, no spend**, under one second even for a 4 MB file: idea and category, place, languages, counts (features after dedupe, roles, apps, integrations, references, facts by kind), Compass tier and degraded flag (information only, never an input), **research load, class (Tiny, Small, Medium, Big), light mode yes or no**, signals, `trust` on or off **and why**, planned topics by job, template-request and weak-geography warnings, declined topics, and an **estimate** (searches, pages, minutes, cost with a range) from a data file seeded with your dry-run numbers plus the check-all cost and **calibrated from the spend record** once real runs exist (label it "estimate, not measured").
- Uploads (`POST`, 25 MB limit) are validated the same way and stored in `uploads/`. A run copies its input into the run folder at the start (later edits do not change a run; the UI shows "changed since this run").

### 6.4 Budget and spend record (RC-0 lives here)
- **Owner decision: USD 5.00 in total, restartable, recorded, never exceeded; no per-run cap and no call-count cap.** Remove or neutralize `RESEARCH_RUN_CAP_USD` (not binding) and keep `RESEARCH_LIVE_BUDGET_USD=5.00` as the total. **Tripwire at 4.50:** the run in progress finishes, no new run starts. **Hard stop at 5.00:** a call that would pass it is refused and the run commits `partial` with `budget_stop`.
- **Restart:** archive the current shared live-spend ledger (about USD 2.37 so far; never delete history) and start this work at 0.00. Set the repo guard so that its own margin (your report: about an 80% tripwire and a 95% effective cap) still lets **5.00 be the real ceiling**; change nothing else in the repo's cap policy; record it as a decision; tell the owner the exact environment values.
- **Spend record** (`spend-record.json`, schema versioned): periods (with archive and restart history), and one entry per live action (kind: run, bake-off, probe, ping, smoke; run id; input; USD by step: search per provider, plan, queries, extract, check, assemble, probe; running total since the restart). **Write as the run goes** (a crash must not lose spend) and reconcile with the gateway ledger at the end of the run; the record must equal the ledger delta. Expose `GET /api/budget`, `GET /api/spend`, `POST /api/budget/restart` (body `{"confirm":"RESTART"}`; refused while a run is active). Show the running total in every run summary.

### 6.5 Preflight
`GET /api/preflight` returns plain checks (id, label, ok, detail, fix): each provider key present (boolean); inputs folder found and how many valid files; data folder writable; store ready; budget status; UI assets present; gateway routes configured; model name in use; time. `POST /api/preflight/ping` (explicitly labelled "about USD 0.01") does one search and one tiny model call, books them, and shows the result.

### 6.6 Runs, queue, API
- **One run at a time by default** (`RESEARCH_MAX_CONCURRENT_RUNS`, default 1): further starts queue (`queued`, position shown, cancellable) and start automatically. One active run per input (a second start returns the active run). Idempotent actions.
- Keep the existing endpoints (`docs/api/research-agent.md`). Add (names are suggestions; document them): `GET /api/session` (the dev token for same-origin calls), `GET /api/inputs`, `GET /api/inputs/{id}`, `POST /api/inputs/upload`, `POST /api/runs` (`{input_id}`), `GET /api/runs`, `GET /api/budget`, `GET /api/spend`, `POST /api/budget/restart`, `GET /api/preflight`, `POST /api/preflight/ping`, `GET /api/settings`, `POST /api/settings` (`primary_provider`), `GET /research/runs/{id}/report`, `GET /research/runs/{id}/spot-check`, spot-check verdict endpoints, `GET /research/programs/{id}/latest?view=compact`, `GET /research/programs/{id}/decisions`, a paged and filtered review endpoint (`limit`, `offset`, job, lane, evidence, flags, impact, text), `GET /api/health`.
- Bind to localhost; reject state-changing requests whose `Origin` is not the app's own (a web page elsewhere must not be able to start spending); no CORS; a strict content-security policy and `X-Content-Type-Options`; structured logs to `logs/app.log` with rotation; a global error handler so one bad request or task never stops the server.

### RC-0 (Phase A). Budget restart and spend record: section 6.4.

### RC-1 (P0). No silent drops: main store, appendix, compact view
**Change.** Remove the drop loop and `dropped.size_cap`. Replace `research_tokens` and `slice_tokens` in `data/ceilings.yaml` by `store_tokens: 40000`, `chunk_items: 120`, `digest_tokens`. New pure module `assemble/store.py`: per item `rank`, `tokens_est` (characters over 4, on the **compact view**) and `store` (`main` or `appendix`, with `appendix_reason`). **Protected (always main):** an item linked to a Brief id (not `NEW`) with `impact: high` or kind `rule`, `compliance_note` or `service_option`; items flagged `conflict` or `needs-confirm`; the best two of every kind. **Rank for the rest, best first:** Brief-linked, high impact, evidence (`official`, `corroborated`, `single_source`, `unverified`), then norm level as a tie-break only, then job priority, then id. If the protected set alone exceeds the limit, keep all and warn. **Compact view** (`GET .../latest?view=compact`, a deterministic projection, not a second stored file): main-store items, norms, gaps, confirm, suggestions and defaults, with **sources in one table** and `use_note` only when it differs from the kind default; `profile.store_tokens`, `profile.appendix_items`, `profile.digest_tokens`. Slices list **every main-store item of the lane**, ordered by code, split into `chunks[]` of at most `chunk_items`; digests are an index, outside `store_tokens`. RV-09 and RV-22 become **enforced**. **Threshold:** `store_tokens` (default 40,000) is a config value; read the model's real context window, output limit and prices from the gateway, report them (they are unverified), and expose the routing threshold in `profile` so Spec can decide between the whole store and packs.
**Acceptance.** Above the limit, items move to the appendix and `len(items)` is unchanged; a Brief-linked high-impact `limited_evidence` rule stays while a generic `core` normal-impact item goes; atoms equal items plus merged; slices hold all main-store items of a lane and split above `chunk_items`; the compact view is smaller with the same ids; hashes stable; no `size_cap` left.

### RC-2 (P0). Check every item, inside the topic, before the audit
**Change.** Move the check into the worker (after verify): all verified atoms of the topic, in batches of 15 (`CHECK_BATCH`), **in parallel across topics** under the model semaphore, **before** `update_coverage`. New `rsch.check` v2: per item the claim, the typed `data` (compact JSON), the **passage window** (about 150 words around the quote, from the normalized page text using the offsets of quote verification), the page title and domain; output `verdict` (`supported`, `partial`, `not_supported`) and `unsupported_fields[]` (paths in `data`). Code: null unsupported fields; if the item then lacks its kind's minimum, drop it as `thin` (`unsupported_field`); `partial` adds `partial_support` and evidence `unverified`; `not_supported` rejects the atom and **the slot reopens**; a failed call or missing verdict leaves the item `unchecked` and `unverified` (never trusted, never dropped silently). Check **identical (claim, quote) pairs once**. The run clock and the budget tripwire cover checks and assembly (after the hard time ceiling no new batch starts; the rest is `unchecked`). Skip and topic cancel propagate into in-flight checks.
**Acceptance.** A `not_supported` verdict on the only item of a required slot reopens it and a follow-up query is issued; two topics' checks overlap (fake clock); every verified atom has a verdict or `unchecked`; an unsupported `type` is nulled; check cost has its own call id; determinism with random delays.

### RC-3 (P0). Ground numbers, attributes, dates; read tables; stop clipping
**Change.** New `core/numbers.py` (pure): extract numbers, amounts, percentages, ranges and dates from the claim, label and numeric `data`; normalize (Unicode digits to ASCII, separators, decimal points, currency symbols and codes, `lakh` and `crore` as written, number words one to twelve, "per cent"); each must occur in the normalized quote. **RV-18:** if absent from the quote but present in the passage, widen the stored quote to the smallest enclosing sentence (at most 40 words, flag `number_widened`); else reject `number_not_in_quote`. **Extraction prompt and kind guides:** state only what the passage states; types, required flags, allowed values, steps and states the page does not give are `null` or omitted; remove the phrase quoted in 3.3; update `domain/atoms.py` (nullable attributes, new minimums). **Keep the richness (section 1a, D1):** the instruction to return as many distinct, specific items as the page supports stays; grounding removes invented details, not true ones. **Dates:** the page metadata date, else a date parsed by code from the quote, title or URL; the model's date is ignored. **Claims:** cut only at a sentence end within 40 words, else reject `claim_too_long`. **Merge:** mark ordered fields (`steps`, `transitions`) in the kind schemas and never concatenate them across sources (keep the richest list, store the others as `variants`). **Use-note guard:** numbers as whole tokens, case-insensitive words, first word included; RV-05 enforced. **Page reading:** make sure the main-text extractor keeps **table cells and list items** (pricing and fee pages); detect **soft 404 and wall pages** by title, headings and the first 2 KB, not only on short pages; add fixture pages for each.
**Acceptance.** Property and golden tests: `₹5,000` against "5000"; `2.5%` against "2.5 %"; `10-15 days`; `Rs. 1.2 lakh`; Devanagari digits; "two" against 2; dates; a missing number is widened or rejected; the model's `published_on` is ignored; a 55-word claim is cut or rejected; two step lists keep one list plus `variants`; a quote from a table cell verifies; a soft-404 page is skipped; the prompt no longer asks for types or allowed values.

### RC-4 (P0). Independence by content; region and entity fit
**Change.** Apply the existing content-overlap rule (`core/sources.py`: 5-word shingles, 0.8) in norms and corroboration (RV-19), and to the quote's passage window; flag `duplicate_source`. The extractor returns `about_region` (ISO 3166-1 alpha-2, `global` or `unknown`) and `about_entity`. **RV-20:** a different specific country than the plan's place gives `other_region`; an anchored topic whose `about_entity` shares no stem gives `other_entity`. Flagged items are excluded from corroboration, norms and prevalence, get evidence `unverified`, stay (appendix-eligible, shown in the report).
**Acceptance.** The same paragraph on two domains counts once, a paraphrase twice; a regulator page for another country is flagged and raises no norm; a namesake company is flagged; both flags show in the report.

### RC-5 (P0). Readable report, evidence views, spot-check data

## 10. Optimization (measure first, then change; report before and after)
OPT-1 **skip pages with no relevant passage** (a minimum passage score in data) so no model call is wasted; count skips. OPT-2 **extract once per page** when several topics select it in the same round (union of wanted kinds), only if measurements show duplicate extraction. OPT-3 **check identical pairs once** (RC-2). OPT-4 prompt prefixes stable for gateway caching (AD-26) where supported. OPT-5 the stage timings of RC-7 decide where latency work is worth doing; raise lanes up to the gateway limits only if rate limits allow. OPT-6 the search cache holds raw provider text: cap the size of cached entries and report memory. OPT-7 the front end budgets of section 7. OPT-8 startup: lazy imports, the preview cached by (path, size, mtime). Do **not** add a persistent page cache, a cross-run model cache or batch calls inside a run (decisions AD-58).
