## 1. The product, in one minute (so you understand why)

Mobigen is an enterprise AI mobile-app builder. A person describes an app; the system produces a complete Expo / React Native app (TypeScript strict). The first engine is the **Context Engine**: four agents in a line, each writing one file.

1. **Compass** (built): interviews the user and writes the **Brief**; the user approves it at **Gate 1** (hash-bound, immutable after approval). Its full export (format 2) holds the Brief with stable ids (features `FTR-###`, roles `ROL-###`, apps `APP-###`, modules `MOD-###`, flows `FLW-###`, entities `ENT-###`, research requests `RR-###`), tiers (Locked, Default, Open), consumer views (including a `research` view) and an intent-level structure.
2. **Research (you build this now):** after Gate 1, searches the web for what the model cannot know (comparable products, regional providers and APIs, fees and rules as information, data shapes, local formats) and hands **Spec** one structured, verified file.
3. **Spec** (not built): one agent with three lanes (Product, Design, Screens) that turns Brief + Research into the Blueprint, Design and Screens. **It reads your output directly.**
4. **Verify and package** (not built): independent proof and the single `APP_SPEC.md`. Then the Front-end engine builds the app from it, then Backend and QA.

Why Research matters: a good small, medium or big app needs a detailed, correct spec. The user cannot supply what the world knows (what comparable apps include, which payment providers work in their city, which fields a GST invoice needs). Research brings it, **sourced and verified**, and never decides scope.

Research runs **in the foreground, visible**: it starts when the user approves Gate 1, shows live events in the front end, and Spec starts when it commits (or when the user presses Skip).

## 5. What Research does, in plain terms

From an **approved Compass Brief** (format-2 export) it: decides how much research the idea needs from the **content of the Brief** (never from the Quick, Standard or Thorough tier); works out the Spec decisions that matter for this kind of app and idea; runs parallel workers that search the web with specific, entity-anchored queries for **how things are usually done, how common each choice is, and what is current**; reads the pages; extracts typed facts each with a verbatim quote that **code verifies**; computes prevalence and recency; checks important facts with a second model and independent sources; goes back only for what is still missing; assembles one detailed **playbook** `research.json` **indexed by the Brief's ids and organized per Spec lane**; and streams live events to the front end. It never decides scope and never marks anything Locked.

### 6.1 Inputs, trust, and the research load
- Input: the Compass **format-2 export** (JSON) via the API (6.9). Check `export.approved_baseline.hash == brief._hash == export.brief_hash` and refuse a run otherwise (RV-13). Do not import Compass to recompute; equality is enough (use a shared hashing utility only if one exists outside `agents/compass`).
- Use `consumer_views.research` as the main contract (idea, geography, languages, audience, references, feature_intents, glossary, research_requests, search_hints, declined, modules, entities, domain_facts, `guidance.focus`). Look up **tiers and ids in `brief`** (the view is values-only) until Compass adds tier tags. Work with and without the new Compass trust fields (`quality`, tier tags, request `origin`; prompt 04) and **derive and flag** what is missing.
- **The tier is not an input.** Ignore `guidance.size_band`, `depth`, `search_budget`, `max_requests`.
- **Research load** (data file `data/load.yaml`): `load_score = deduped features + facts of kind rule/compliance/integration_detail/nfr + 3 × apps + 5 × sensitive-data flags + 2 × named references`. Classes: **focused** < 25, **standard** 25 to 60, **deep** > 60 (calibrated on the three real runs: about 17, 31 to 41, 95; retune with evidence and report).
- **Starting defaults by class** (data file; soft, tune for result quality): searches about 20 / 40 / 80; pages read about 24 / 60 / 140; time about 3 / 6 / 10 min (if coverage is still improving, let the run continue and show "taking a bit longer"; Skip is always available); rounds 2 / 3 / 3; parallel lanes (search / extraction) 6 / 8, 8 / 12, 10 / 16; `research.json` about 12k / 20k / 32k tokens; per-lane slice about 4k / 7k / 11k. A covered topic simply stops early; these are not targets. Prefer more verified, useful detail over less; shape what Spec reads through the slices and digests.
- **Trust rules (Compass author's corrections, binding):** read values by tier (Locked = the user's verified words; Default/assumed = AI guess); "Approve all" is not review; `meta.interview.fallback_count` is **not** a full failure counter (timeouts with 0 tokens are missed; recompute from `spend.by_call` when present, and treat requests as **template text** when they show template patterns); the structure is a **hint** only (Thorough's is mostly fallback; never anchor a query on screen counts or names, never use structure counts in the load score); `later` priority does not mean defer; roles and features may be duplicated (singular and plural; two names for one thing): dedupe before building terms; do not use `open_questions` or assumptions as search seeds (junk tokens); weak Locked geography (for example a city taken from a data-residency quote) sets `geo_uncertain` (use the country plus every stated city); do not search the user's own brand name alone (its facts come from the Brief; a website or reference URL the user gave is read as a seed source; named *references* are searched, and one that cannot be told from the user's own brand is `ambiguous`); respect `declined`.
- Detect **template or thin requests** (request `origin: template` if present, repeated words like "app apps", the same audience list in most requests, empty `search_hints` with no regional entity) and **rebuild the plan from facts** (`plan_source: rebuilt`).
- Build `input_quality` (request counts by trusted/template/thin, plan_source, degraded, failing probes, structure source, geo_uncertain).

### 6.2 Jobs: organized by what Spec must decide
Eight jobs (slot schemas in data files; minimums are starting points, more verified detail is better). Every topic carries a `spec_need` and a `lane`:
- **features** (Scope, BLUE-1; lane blueprint): comparable and local apps; features by commonness (core, common, advanced, emerging); recent additions; pricing models. Slots: 3+ competitors each with 5+ features (level); norms for 8+ features with prevalence.
- **structure** (screens, navigation, roles; blueprint): the usual screen inventory per app and role; navigation patterns and when used; usual roles and what each does; module grouping. Slots: 8+ typical screens with purpose and role; 1+ navigation pattern; roles with 3+ typical tasks.
- **flows** (journeys; blueprint, screens): usual journeys per role with steps, alternates, exceptions; onboarding; empty, failed and offline cases. Slots: per main journey 4+ steps, 1+ alternate, 1+ exception.
- **data** (entities, lifecycles, rules; blueprint): usual entities, fields (type, required, values, validation), relations, statuses and transitions, business rules and formulas, KPIs; regulatory rules as information (`legal-adjacent`). Slots: per main entity 6+ fields and states where a lifecycle exists; rules with value, unit, source.
- **services** (contract, integrations; integrations): providers by need (payments, OTP and messaging, maps, telematics, identity, government portals): auth, endpoints or events, sandbox, limits, fees, regional fit, current status. Slots: per need 2+ providers with auth, events, sandbox.
- **design** (look and feel; design): category UI and UX conventions: layout and navigation patterns, onboarding, component patterns, colour and tone mood, typography and density, iconography, motion, accessibility; platform guidelines (Apple HIG, Material) as official sources; script and font needs; recent design trends. Slots: 6+ `design_convention` items across 4+ aspects; a script need when the locale is not Latin.
- **screens** (per-screen content; screens): for each usual screen pattern: sections, key components, actions, states (loading, empty, error, success), validations, microcopy conventions. Slots: patterns for the 5+ most important screens (more for deep loads, per module cluster).
- **local** (mock data and formats; mock): formats and ID patterns with validation patterns and examples; local terms and units; realistic names, price ranges and edge cases. Slots: formats where unusual; 10+ realistic examples for the main entities.
Regulations and compliance are information inside `data` and `services`, flagged `legal-adjacent`.
**Two layers per job:** the **category norm** (how apps of this kind usually do it, from several comparable sources) and the **idea-specific details** (what this Brief's unusual facts need).
**Targets come from the union** of the Spec-need areas that apply to this kind of app, Compass `research_requests`, `guidance.focus` and high-impact `domain_facts` (`focus` can lack topics that the requests cover; `focus.compliance` mixes enum values and sentences: a hint, not a list).
**Norms, not just facts.** Code computes **prevalence** for features, screens, flows, entities, integrations and design conventions: seen in n of N distinct sources or competitors, and a level `core` (most), `common`, `advanced`, `emerging` (recent and rising); fewer than 3 sources is `limited_evidence`. The model assigns normalized keys; code reconciles them.
**Latest.** Features, design and services topics prefer sources from the last 24 months (a time range on the query; `published_on` and `age_months` on every item; older than 24 months flagged `stale`); `trend` items record what changed recently. Regulations and provider facts use the newest official source.

### 6.3 Worthiness gate and query anatomy
A topic is searched if it feeds a Spec decision (`spec_need`) **and** at least one holds: it needs current or regional grounding (providers, fees, rules, trends); a norm needs evidence of how common it is (features, screens, flows, entities, design conventions); it names an entity (from the Brief or found in round 1); it involves a number or an integration's specifics. Skipped (answered from model defaults, flagged `assumed`): pure trivia that never changes a decision (a currency symbol, common date formats). **Norms for the Spec-critical areas are always worth grounding, even where the model knows them.**
Every query contains an **anchor** (named entity, discovered entity, or a domain noun from the user's words), a **place** (Locked geography, or country plus every stated city when `geo_uncertain`) and an **intent word** (features, screens, flow, fees, rules, API, sandbox, limits, design, UX). A category-only query is poor, so do not emit one. Short first (about 4 to 12 words), at most about 25 words, no URLs or key-like strings.
Names from model memory appear **only in discovery queries** and are labelled `entity_from_model`; they are never facts. Seeds from Locked facts first; Default-tier seeds give `assumption_derived` queries, and results never raise a tier.

### 6.4 The per-topic worker (a fixed pipeline, one per topic, in parallel, isolated context)
1. **Query writer** (model, small): sees only its topic, slot schema, anchors and trust flags → 2 or 3 variants: *literal* (named entity quoted, exact match), *descriptive*, *local-language* (when the region's language is not English; Hinglish is searched in English with transliterated terms).
2. **Search** all variants in parallel through `SearchPort` (with a 24-month time range where recency matters); **reciprocal rank fusion** (k=60) and canonical-URL dedupe; source-class ranking and the authority registry (official domains preferred for rules).
3. **Triage:** code score (source class, snippet relevance, domain diversity, at most about 2 per domain); one batched model call only if more than about 12 candidates; keep the best 3 to 5 pages.
4. **Read:** provider page text if present, else `FetchPort`; **passage selection** (BM25 windows around slot terms), not blind truncation.
5. **Extract** (model, no tools), in parallel per page, into the slot-typed record: paraphrase ≤ 40 words, verbatim quote ≤ 25 words, `impact` normal or high, a normalized key (feature, screen, flow, entity, integration, design aspect) and the page's date. Extract as much useful, specific, structured detail as the page supports (screen sections and states, entity fields and enums, steps and exceptions, provider capabilities, numbers), not vague summaries.
6. **Verify (code):** the quote must be a substring of the stored page text after NFKC, whitespace, case, quote-mark, dash and zero-width normalization (RV-02); source URL and date in the fetch log (RV-03). One retry "quote exactly"; else drop. Update slot fill; emit events.
Workers return only verified, typed items. No global barrier between topics (pipeline them).

### 6.5 Rounds, coverage audit, stopping
- Round 1 covers every surviving topic. Then a **coverage audit** (code): a required slot is filled by ≥ 1 verified item (`impact: high` needs 2 independent domains or is flagged `single-source`). A topic with all required slots filled is **covered** and spends no more.
- A **gap analyst** (model) proposes follow-up queries for unfilled required slots and for entities discovered in round 1 that match a slot (including one query restricted to the entity's own domain to read its official pages). Follow-ups must differ from earlier queries; after a couple of distinct follow-ups the topic is `not_found` (a gap listing the attempted queries). That keeps the loop from searching forever for something that does not exist.
- Stop when all topics are covered or `not_found`, or a round adds very little (fewer than about 10% of the remaining required slots), or the defaults in 6.1 are reached and coverage has stopped improving, or Skip. At the end, finish extraction of pages already read and commit (`partial` when something was left unfinished).
- **Checker** (second model, batched): `impact: high` items only; sees claim + quote only; `supported` / `partial` / `not_supported`. Code checks stay primary (quote substring, two independent domains, official first; forum, blog and SEO pages cannot support high-impact claims).
- Per-call timeouts (search about 8 s, page fetch about 10 s, model about 45 s, one retry; tune). **A timeout or a 0-token model call counts as a failure** (`budget.failures`) and shows as a `warning` event. On HTTP 429: back off, tell the user, continue.

### 6.6 Assembly (for Spec)
Code builds: the indexes `by_feature`, `by_role`, `by_entity`, `by_flow`, `by_integration` keyed by **Brief ids** (every `applies_to` id must exist in the Brief or be `NEW`; RV-16); **`norms[]`** (per normalized key: `seen_in` n of N, level core/common/advanced/emerging/limited_evidence, recency, `matches_brief` by fuzzy match); `suggestions` (features, screens, fields, states, validations not in the Brief; always `undecided`, never scope); `confirm[]` (numbers and legal-adjacent facts for the owner to confirm); `defaults_proposed[]` mapped to builder needs (BN-02, 04, 05, 07, 10); `gaps[]`; `conflicts[]`; and **digests**: a compact, code-rendered, table-style text per Spec lane (`blueprint`, `integrations`, `design`, `screens`, `mock`, `verify`), for example the top norms with prevalence and level, the typical screen inventory, entity field tables, provider comparison tables. **One** model call (no tools) selects and orders items per lane and writes `use_note` (≤ 15 words); **it writes no new facts** (RV-05). Do not write sections in parallel.

### 6.10 Providers and ports
- **SearchPort** adapters (plain `httpx`): **Tavily** (`POST /search`: `query`, `search_depth` basic, `topic` general, `country` lowercase country name (only for `general`), `language` ISO 639-1 with `filter_by_language`, `include_domains` with `include_domains_mode` prefer or restrict, `exact_match`, `time_range`, `max_results` ≤ 20, `include_raw_content` for page text) and **Serper** (Google results: `POST https://google.serper.dev/search`, key in the `X-API-KEY` header, body `q`, `gl` country, `hl` language, `num`, optional `tbs`; links and snippets only). **Verify both against the official documentation before coding** and record URL and date in the report; do not trust this summary. Normalize to `SearchHit {url, title, snippet, content?, published?, rank, provider_score}`; support domain preference, domain restriction (Serper: `site:`), exact match, time range, country and language; report which locale parameters were applied (`locale: weak` when not). Log cost per call. **Brave is deferred: do not build it**, but keep the port generic.
- **FetchPort** (in `agents/research/`): trafilatura main-text extraction; PDF text layer (no OCR); the web-hygiene rules of section 3; content hash.
