# How the frontend engine consumes `APP_SPEC.md`

The frontend engine starts only on `spec_ready`, which the Flow controller emits at Gate 2 approval after committing the approved version. It reads the file and builds the app; **it never edits the spec and never talks to the user**. This page is the contract between the Context Engine and that engine (spec section 7, brief 8.5). The file format is in [app-spec-format.md](app-spec-format.md); the library is `mde_spec_loader` ([package page](../packages/spec-loader.md)); `scripts/simulate_frontend_consumer.py` is the executable form of this contract.

## 1. The five rules

1. Check the file first: `SpecIndex.from_path(path)`, then `index.verify(approved_hash)` with the hash from `spec_ready`. A file that does not verify is not built.
2. Follow the build sequence S0..S10 (section 3) in order. Never load the whole file into one prompt: take one `slice()` per task.
3. One task per screen. A screen task gets `index.slice("SCR-014")` and nothing else from the spec (plus code and the kit it needs).
4. A real gap goes to `raise_decision(question, options, default)`; the spec is never patched locally (section 6).
5. Every generated file starts with its `@spec` header; a hand-edited screen is locked and skipped (sections 5 and 7).

## 2. Reading the file

```python
from mde_spec_loader import SpecIndex

index = SpecIndex.from_path("APP_SPEC.md")
assert index.verify(approved_hash)           # untampered, and the version the user approved
spec = index.spec                            # typed AppSpec if you want to walk it
for step in spec.build.steps:                # S0..S10
    task = index.slice(step.id)              # or index.slice("SCR-014") for a screen
    run(task.spec_tag, task.text)            # "@spec SCR-014@v7", the prompt context
```

`index.index()` lists sections and ids with sizes, `index.get(["SCR-014", "ENT-Order"])` returns exact blocks and items, `index.neighbors(id)` and `index.refs(id)` answer graph questions. Token sizes are estimates (`ceil(UTF-8 bytes / 4)`), identical everywhere.

## 3. Build sequence S0..S10

Generated by code from the flows and the reference graph (`mde_spec_builder.sequence.build_sequence`), stored in block `BUILD`, one `BuildStep` per step:

| Step | Name | Loads | Gate (`gate`) |
| --- | --- | --- | --- |
| S0 | Scaffold from the stack template | `APP`, `DESIGN` | `boots_on_web_preview` |
| S1 | Theme and tokens | `DESIGN` | `token_file_validates` |
| S2 | Component kit variants | `DESIGN` | `kit_renders_in_all_variants` |
| S3 | Navigation shell and auth gate | `NAV`, `ROLES` | `all_routes_resolve` |
| S4 | Data layer: types, API client, mock server | `DATA`, `API` | `typecheck_passes` |
| S5 | **Vertical slice**: the primary flow end to end | the primary `FLW-###` and its screens | `user_feedback` (**stop for feedback**) |
| S6 | Screen groups in parallel | each screen block plus references | `screens_render_in_all_states_and_checks_pass` |
| S7 | Global behavior wiring | `BEHAVIOR` | `flow_tests_pass` |
| S8 | Integrations: mocks and adapters | `INTEGRATIONS` | `adapters_typecheck` |
| S9 | Polish and accessibility | `DESIGN`, `BEHAVIOR` | `lint_and_accessibility_checks_pass` |
| S10 | Hand off to QA | `ACCEPT` | `release_gate` |

- **S5** has `flow`, `screens` (the flow's screens, in order) and `stop_for_feedback: true`. The primary flow is the first flow marked `primary`; otherwise the flow with the most screens (lowest id on a tie); with no flow at all, the first navigation screen and what it reaches through actions (at most five screens). S5 is built by one agent, so its screens are not in any S6 group. At the stop the frontend engine uses its own approval point (outside the context flow) to show the slice.
- **S6** has `parallel` groups. Every screen that is not in S5 is in exactly one group. Groups follow the flows (a screen's own `flow`, else the first flow listing it) and fall back to the screen's surface for screens in no flow. Each group has `owns`: path globs it may write.
- **`owns` globs** are literal paths under `app/` with `**` meaning "this whole subtree"; `[id]` is a literal Expo Router segment, not a glob class. A group owns `app/<prefix>/**` (plus `app/<prefix>.tsx` if a screen sits at the prefix) when its screens share a path prefix that no screen outside the group uses; otherwise it owns one exact `app/<route>.tsx` per screen. **No two groups own overlapping paths**, and no group owns a vertical-slice screen's file; that is what makes the parallel work safe. Shared code (`components/`, theme, data layer) belongs to the earlier steps.
- A step's `load` lists block ids. Shared files outside the app routes are the steps' own output, not part of a group.

## 4. One task per screen: `slice()`

`index.slice(target)` returns a `Slice`: `id`, `spec_tag`, `text` (the bundle, ready for a prompt), `block_ids`, `token_estimate`, `tiers`, `locked`. `target` is a step id, a screen id or a flow id. The bundle is built in tiers (spec 7.2):

| Tier | Content | Loaded | Typical size |
| --- | --- | --- | --- |
| 0 | Header front matter, summary line, tone, naming, stack rules | always | 1 to 2k tokens |
| 1 | The `DESIGN` and `NAV` blocks | every run | 2 to 4k |
| 2 | The task's own block(s); the entities (with the enums they use), operations, integrations and roles they reference, carved out of their blocks; kit-component signatures | per task | 1 to 2k |
| 3 | Neighbouring screens (`tier3=True`) | on demand | as needed |

A screen task stays well under 10k estimated tokens whether the app has 12 or 50 screens: the 50-screen sample slices at about 3k. The slice never includes the whole `DATA` or `API` block, only the items the screen references (operations it binds or calls, their request and response entities, entities those link to one hop, the enums they use, roles that gate it, integrations it mentions).

- **Kit signatures.** The kit belongs to the frontend engine, so it passes them in: `index.slice("SCR-014", kit_signatures={"detail-with-sticky-cta": ["StickyCta(props: {label: string, onPress: () => void})"]})` maps a recipe id to the signatures of the kit components that recipe uses. They appear in tier 2.
- **Stack rules.** `stack_rules=[...]` adds `Stack rule:` lines to tier 0.
- **Tier 3.** `index.slice("SCR-014", tier3=True, max_neighbors=6)` appends the blocks of the screens linked by navigation, actions or flow order. Ask for it only when the task needs to see a neighbour.
- A `locked` screen comes back with `locked=True` and a `LOCKED:` line (section 7).

## 5. `@spec` headers and staleness

Every generated file carries a header naming the block it was generated from and the version:

```ts
// @spec SCR-014@v7
```

`slice(...).spec_tag` is exactly that string (`@spec SCR-014@v7`); `mde_spec_loader.format_spec_tag(id, version)` builds it and `parse_spec_tag(text)` reads it back from a file (`("SCR-014", 7)`). A file is stale when its tag's version is older than the spec's version **and** its id appears in the stale set of the diff (section 8); other files from older versions are still current and are not regenerated.

## 6. Gaps: `raise_decision`

The frontend engine never interviews the user and never edits the spec. When it hits a real gap (a button with no destination, a field the spec does not define, a conflicting rule), it calls:

```
raise_decision(question: str, options: list[str], default: str)
```

`raise_decision` goes back through the Conversation Engine, which either asks the user once or applies `default` and logs it. The answer comes back as a new spec version (and a `diff`), never as a patch to the file in hand. Anything the nine validators already catch (an action with no destination, a dangling reference) should not reach the frontend engine; `raise_decision` is for what only a person can settle.

## 7. Locked screens

A screen block with `locked: true` was hand-edited downstream. The engine skips it on regeneration, in S5/S6 and in incremental runs. `index.locked_screens()` lists them and `slice()` flags them. A new spec version never overwrites a locked screen's code; if its block changes, the engine raises a decision instead of regenerating.

## 8. Incremental runs from `diff`

For version N+1 the engine does not rebuild everything:

```python
old = SpecIndex.from_path("v6/APP_SPEC.md")
new = SpecIndex.from_path("v7/APP_SPEC.md")
changes = old.diff(new)       # SpecDiff(added, removed, changed, stale_screens)
```

- `added`, `removed`, `changed` are ids of blocks (`DATA`, `SCR-014`, `DESIGN`, ...) and of the items inside them (`ENT-Order`, `API-getProduct`, `ROLE-admin`, `NAV-007`, `ENUM:OrderStatus`). `HEADER` and `REV` are meta and never listed.
- `stale_screens` are the screens to regenerate: screens that changed or were added, plus screens that use a changed, added or removed entity, operation, role, integration, enum or navigation node (in either version).
- Global steps by block: `DESIGN` changed means S1/S2 (and S9 polish); `NAV` or `ROLES` means S3; `DATA` or `API` means S4; `BEHAVIOR` means S7; `INTEGRATIONS` means S8; `ACCEPT` means S10. A removed screen's files are deleted unless it is locked.
- Locked screens in `stale_screens` are not regenerated (section 7).

## 9. The consumer simulator

```
uv run python scripts/simulate_frontend_consumer.py APP_SPEC.md [--budget 10000]
```

Walks the build sequence of a spec file the way the frontend engine will: slices every step and every screen, prints the token size of each, and exits non-zero when:

- a slice exceeds the budget (default 10 000 estimated tokens);
- a reference does not resolve (an action, binding, navigation node, flow, role gate, research reference or build step that names an id the file does not have);
- a screen is built by no step, or by more than one;
- the embedded hash does not match the file;
- a step loads an id the file does not have.

Exit code 0 means ok, 1 a contract violation, 2 an unreadable or unparsable file. It is a contract test, not a code generator; the same logic is available as `mde_spec_loader.simulate_consumer(index, budget_tokens=...)` for the CLI (`mde spec simulate-consumer`) and the end-to-end tests, which run it on every golden spec.
