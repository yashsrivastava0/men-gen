# Data model (PostgreSQL)

Owner: `persistence-engineer`. Source of truth for the schema: `packages/persistence/src/mde_persistence/models.py` (SQLAlchemy 2.0 declarative) and the append-only Alembic revisions in `packages/persistence/src/mde_persistence/migrations/versions/`. A drift test fails the build if the two disagree. Package guide: [packages/persistence.md](../packages/persistence.md). Spec section 11 is the product-level list; this page is how it is stored.

## Principles

- **PostgreSQL 16+ only** (JSONB, `FOR UPDATE SKIP LOCKED`, advisory locks, partial unique indexes, `ON CONFLICT`). One driver for runtime and migrations: psycopg 3 (`postgresql+psycopg://`). No SQLite, not even in tests.
- **Ids** are prefixed ULIDs stored as `text` (`ses_`, `job_`, `apr_`, `crd_`, `evt_`), generated by `mde_core.ids.new_id`. Rows that belong to a session use composite keys `(session_id, version)` or `(session_id, event_id)`.
- **Timestamps** are `timestamptz`, always UTC. **Money** is integer micro-dollars (`llm_call.cost_micros bigint`). No floats for money.
- **JSONB vs relational.** The record tables keep the full Pydantic record as JSONB (`session.discovery`, `brief_version.brief`, `research_note.note`, `spec_version.spec`/`plan`, `session_event.payload`, `job.payload`). That JSONB is the **source of truth** and is what repositories read back. A few relational **projections** are maintained by the repositories when the owning record is saved so they can be queried and joined; they are never read back into records:

  | Projection | Maintained by | From |
  | --- | --- | --- |
  | `slot` | `SessionRepo.create` / `save` (rewritten each save) | `session.discovery.slots` |
  | `card_instance` | `EventRepo.append_outbound` (shown), `EventRepo.record_inbound` (answered, skipped, "you decide") | `card` outbound events and `option_selected` inbound events |
  | `research_job`, `research_fact` | `ResearchRepo.add` | `research_note.note.facts` (job, kind, statement, impact, confidence, verified, primary URL, retrieval date, all sources) |

- **Decisions on names.** `spec_draft` is a row of `spec_version` with status `draft` (one table, one set of immutability rules). The spec's `turn` event log is `session_event` (inbound and outbound events in one table, the SSE replay source). There is no separate `idempotency_key` table: the primary key `(session_id, event_id)` of `session_event` is the idempotency guarantee for inbound events. Tenants are created implicitly the first time a tenant stores something (dev headers carry only an id).
- **Content columns never use free-form user text as identifiers.** NUL characters (which PostgreSQL rejects in `text` and `jsonb`) are stripped from stored strings.

## Indexes and constraints that carry business rules

| Rule | Mechanism |
| --- | --- |
| One active (queued or running) run per session | partial **unique** index `uq_job_one_active_per_session` on `job (session_id) WHERE state IN ('queued','running')`, plus an advisory transaction lock in `enqueue_plan` |
| Idempotent inbound events | primary key `(session_id, event_id)` on `session_event`, written with `ON CONFLICT DO NOTHING` |
| Strictly increasing, unique outbound `seq` per session | unique `(session_id, seq)`; the value comes from `session.outbound_seq` (see concurrency) |
| Tenant consistency of child rows | composite FK `(session_id, tenant_id)` to `session` |
| Approved spec versions are immutable | trigger `spec_version_guard` (see below) |
| Job and spec/brief statuses are closed sets | CHECK constraints (`job.state`, `job.kind`, `spec_version.status`, `brief_version.status`, `session_event.direction`, `memory_item.scope`) |

Access-pattern indexes: `session (tenant_id, owner_id, updated_at)` (list a user's sessions, newest first), `session (tenant_id, app_id)`, `session_event (session_id, in_reply_to)` partial (replies to an inbound event), `card_instance (session_id, card_id)`, `approval (session_id, gate, version)`, `spec_version (session_id, status)`, `research_fact (session_id, job)`, `llm_call (session_id, at)` and `(scope)`, and for the queue `job (created_at, id) WHERE state='queued'` (claim), `job (heartbeat_at) WHERE state='running'` (recovery), `job (state, created_at)`, `job (session_id, created_at)`.

## Tenant isolation

Enforced in the repository layer and backed by the schema:

- `Store.begin(tenant_id)` binds a unit of work, and therefore every repository in it, to one tenant. Every query filters by `tenant_id`. A session id (or job id, event id, ...) that belongs to another tenant behaves exactly like an id that does not exist: reads return `None` or an empty list, writes raise `NotFound`.
- A record whose `tenant_id` differs from the repository's tenant is refused with `TenantViolation` (`create`, `save`, `add`, `enqueue_plan`).
- `Store.begin(None)` is **system scope**: only `JobRepo.claim` and `JobRepo.recover_stuck` work there; every other repository call raises `TenantViolation`. Conversely a tenant-bound unit of work cannot claim or recover jobs. After a claim the worker continues bound to the job's own tenant.
- Composite foreign keys make it impossible to insert a child row whose tenant differs from its session's tenant, even with raw SQL.
- The store contract suite (`mde_persistence.testing_contract.check_tenant_isolation_everywhere`) proves this for every repository.

## Concurrency and idempotency rules

- **Sessions** use optimistic concurrency: `SessionRepo.save(rec, expected_version=n)` is `UPDATE ... WHERE id AND tenant_id AND version = n` and returns the stored row with `version = n + 1` and a new `updated_at`. No row updated means `Conflict` (stale write) or `NotFound`. Two concurrent saves from the same version: exactly one wins. `get(for_update=True)` takes a row lock for callers that want to serialise a whole turn.
- **Inbound events**: `record_inbound` inserts with `ON CONFLICT (session_id, event_id) DO NOTHING`; `False` means a duplicate (nothing stored, no projection applied). Concurrent deliveries of one event store it once.
- **Outbound events**: `append_outbound` first does `UPDATE session SET outbound_seq = outbound_seq + 1 ... RETURNING`, which takes the session row lock until commit. Appenders for one session are therefore serialised: `seq` is unique, strictly increasing, and equals commit order (a replaying client never sees seq 5 before seq 4). Appending does not touch `session.version`, so it never makes a `save` stale. A rolled-back transaction rolls the counter back too; gaps are possible only through a duplicate event id inside one transaction. `in_reply_to` is stored and indexed; `replies_to` returns the answers to an inbound event in `seq` order.
- **Constraint violations never poison a transaction.** `add`/`create` use `ON CONFLICT DO NOTHING ... RETURNING` and raise `Conflict` themselves, so a caller can catch the `Conflict` and keep using the same unit of work.
- **Versioned records** (`brief_version`, `research_note`, `spec_version`, `approval`) are insert-only; adding an existing `(session_id, version)` raises `Conflict`.
- **Commit and rollback**: `Store.begin` commits on clean exit and rolls back on any exception; `uow.commit()` commits early and the unit of work stays usable. A unit of work holds one pooled connection for its whole block (pool: 5, no overflow): do not keep one open across an LLM call or an SSE stream.
- Time comes from an injectable `Clock` (default `SystemClock`), so queue recovery is testable with a fake clock.

## Spec version immutability

`SpecRepo.set_status` is the only mutation of a stored version. Legal moves: `draft -> approved | superseded`, `approved -> handed_off | superseded`; repeating the current status is a no-op; anything else raises `Conflict`. `git_sha` and `approved_at` may be set once (moving to `approved` stamps `approved_at` from the clock when none is given); a different value later raises `Conflict`. `SpecRepo.add` on an existing `(session_id, version)` raises `Conflict`, so content can never be replaced.

The same rules live in the database as the trigger `spec_version_guard` (`BEFORE UPDATE OR DELETE`): content columns (`spec_text`, `spec`, `plan`, `hash`, `version`, `brief_version`, `research_version`, `created_at`, ids) can never change, status moves are limited to the table above, `git_sha` and `approved_at` cannot be rewritten once set, and non-draft rows cannot be deleted. A bug or a raw SQL session cannot silently edit an approved version.

## Queue semantics (`job`)

States: `queued -> running -> succeeded | failed | cancelled`; a failed attempt or a recovered job goes `running -> queued` while attempts remain.

| Operation | Behavior |
| --- | --- |
| `enqueue_plan(session_id, tenant_id, payload)` | Takes `pg_advisory_xact_lock(hash(session_id))`, refuses with `Conflict` if the session has a queued or running job (the unique partial index is the backstop), inserts `queued` with `max_attempts` from the store (default 3). |
| `claim(worker_id)` (system scope) | One statement: pick the oldest queued job `FOR UPDATE SKIP LOCKED`, set `running`, `lock_owner`, `heartbeat_at = now`, `attempts + 1`. Each queued job goes to exactly one of any number of concurrent claimers; locked rows are skipped, never waited for. |
| `heartbeat(job_id, worker_id)` | Refreshes `heartbeat_at` only if the job is running under that worker; otherwise `Conflict` (the worker lost its lock) or `NotFound`. |
| `set_phase(job_id, phase)` | Records `research` or `build` on an active job; kept across retries so a retry can resume. |
| `complete(job_id, error=None)` | Job must be running (else `Conflict`). No error: `succeeded`. With an error: if cancellation was requested, `cancelled` (no retry); else if `attempts < max_attempts`, back to `queued` (the error is kept as the last error); else `failed`. |
| `cancel(session_id)` | Marks the active run `cancel_requested`. A still-queued job is cancelled outright (state `cancelled`, the slot is free at once); a running one keeps running until its worker sees the flag. Returns whether a run existed. |
| `is_cancel_requested(job_id)` | The flag the worker polls. |
| `recover_stuck(older_than_seconds)` (system scope) | Running jobs whose heartbeat is older than the threshold (by the store's clock): `cancelled` if a cancel was pending, `failed` if no attempts remain, otherwise `queued`. Returns how many jobs were released. |

`mde_persistence.worker.JobWorker` heartbeats while the handler runs and bridges `is_cancel_requested` to the handler's `CancellationToken`; if its heartbeat is rejected it cancels the handler and does not complete the job. `InlineJobRunner` runs queued jobs inline for tests. See [packages/persistence.md](../packages/persistence.md).

## Migrations

Alembic, append-only (`.claude/rules/migrations.md`): never edit an applied revision, add a new one. `just migrate` runs `uv run alembic -c packages/persistence/alembic.ini upgrade head`; the URL comes from `DATABASE_URL` through `mde_core.settings` (default: the private dev cluster on port 54329, database `mde`). Revision `0001` creates everything above, including the partial unique index and the spec guard trigger. Tests apply migrations to an empty ephemeral database, round-trip `downgrade base` / `upgrade head`, run the exact CLI command, and compare the models to the migrated schema with autogenerate (the build fails on drift).
