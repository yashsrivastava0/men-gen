# mde_compass: Compass, the first agent

`agents/compass/` (import `mde_compass`, call ids `cmp.*`, API prefix `/v1/compass`, dev port 8110). The agent a person meets first: it interviews them with question cards and free text (English, Hindi, Hinglish), fills a catalog of slots and writes the **Brief**, one `brief.json` that is hashed, versioned and evidence-tiered, then waits for Gate 1. Behaviour source: [doc 11](../architecture-v3/11-discovery-agent-design.md) (section 17 for the AI-planned interview). Decisions: [ADR 0012](../adr/0012-compass-package-boundaries-and-layering.md) (boundaries), [0013](../adr/0013-brief-schema-v1-hashing-and-versioning.md) (Brief), [0014](../adr/0014-call-spec-registration-from-agent-packages.md) (calls), [0015](../adr/0015-ai-planned-interview-and-interview-memory.md) (AI-planned interview and Interview Memory), D-084 to D-099 in the [decision log](../implementation/DECISIONS.md). Companion pages: [call catalog](../prompts/compass-calls.md), [HTTP API](../api/compass.md), [runbook](../runbooks/compass.md), [package README](../../agents/compass/README.md).

Compass sits next to the older Discover engine ([discovery](discovery.md)), which it does not replace in the running system yet and does not import. Today Compass runs as its own app; nothing in `mde_flow` calls it, and the hand-off to a Research agent is a logging stub (see Limitations). It reads documents and links (PDF, Word, Excel, PowerPoint, CSV, text, Markdown, email, web pages) as well as taps and text, and carries 17 call folders, 46 named edge-case scenarios and 10 persona scripts that run offline.

**Work in progress.** The questions used to come from a fixed catalog of frames and the model only reworded them. The **AI-planned interview** (build prompt 02, ADR 0015) replaces that: the model plans project-specific batches of questions, code validates them, and every question, answer and fact is stored. It is built and tested behind an engine flag (`InterviewPolicy.engine`): `legacy` (the frame engine) is still the default until the planner is switched on in Phase 7, and the legacy path is deleted in Phase 8. Sections below say which engine a statement is about. The front end for the new features is being built separately in `apps/web/`.

```
uv run pytest agents/compass -m "not integration and not live"   # offline, no database (just compass-test)
just compass-test-int                                               # store tests against the private PostgreSQL
cd agents/compass && PYTHONPATH=src python -m evals.run_personas  # the ten persona scripts, offline, prints the metrics report
```

## Architecture

```
HTTP (api/)  ->  CompassService port  ->  Service (engine/service.py)
                                            |  ports (engine/ports.py): 17 call ports + HandoffPort
                                            |  engine functions: state, slots, voi, cards, assumptions, gate, patch, validate, router,
                                            |    document_flow (claims to Brief writes), app_structure, flows/* (targeted flows)
                                            |  InterviewController (engine/interview.py): the planner engine's loop, with the pure
                                            |    modules facts, quotes, fact_projector, needs, terms, context_pack, question_validators,
                                            |    question_pipeline, interview_policy, interview_compile
                                            |  intake/: parsers, chunking, SSRF-safe URL reader, ingest pipeline
                                            |  views/: BriefViewModel, consumer views, readiness, diff, provenance
                                            +--> Store port (store/ports.py): InMemoryStore | PostgresStore
 calls/<name>/adapter.py  --implements--> a call port  --uses--> CallRunner --> GatewayClient --> mde_llm_gateway
```

* **Ports and adapters.** The engine depends on Protocols over domain types (`engine/ports.py`), never on wire models. Each `calls/<name>/` folder ships an adapter (`...Adapter(runner, catalog)`) that builds the wire input, runs the call through `CallRunner`, applies code validators and returns a domain object. `calls/registry.py` (`PORT_BY_CALL`) maps folder names to `Ports` attributes and builds the `Ports`; a folder that has no adapter yet would get a deterministic placeholder (`engine/fallback_ports.py`, flagged `used_fallback`). All 17 folders have an adapter, so no placeholder is in use today. The deterministic fallbacks double as test doubles.
* **`Service`** (`engine/service.py`) implements the `CompassService` port the API talks to. Plain code controls the flow: the model never chooses what happens next, it fills schemas. One event at a time per session (an in-process lock queues events; the store's `try_begin_turn` is the cross-process backstop). A turn has **three phases**, because a transaction never spans a model call (ADR 0004): (1) read and claim the turn (record the inbound event idempotently by `event_id`, `try_begin_turn`); (2) think (load the session, Brief, questions, the Interview Memory and the last 6 transcript lines; run ports and pure code); (3) write everything in one unit of work (new Brief version, change set, asked and answered questions, new and changed facts, question-and-answer rows, batches, summary, session row, outbound events), then release the turn. A turn may end by asking for an **internal follow-up turn** (round 0 does, see below); `handle_event` runs it straight after, as its own turn with its own idempotent event id. Hand-off, when due, is called after the commit. The service keeps its budget object as `Service.budget_guard` (the `budget()` method serves the snapshot). A failure inside a turn becomes one `error` event with code `turn_failed` and the generic text, never a stack trace.
* **The Brief is the single source of truth.** Slots are rebuilt from the Brief on every turn (`slots_from_brief`); a changed hash means a new version. A change to the `meta.interview` audit block alone is also saved (as a new version) although it does not move the hash.
* **Store.** `Store.begin(tenant_id)` opens a tenant-bound unit of work with `sessions`, `events`, `briefs`, `questions`, `change_sets`, `call_log`, `sources`, `contributors` and, for the Interview Memory, `qa`, `facts`, `summaries`, `batches`. Two implementations (PostgreSQL, in-memory fake) pass one shared contract suite (`store/contract.py`, ADR 0007). Rules: a foreign tenant's id behaves as not found; one active turn per session; the Brief `save_version` must be `latest + 1` or `Conflict`; saved versions are append-only and only `mark_baseline` labels one, once; inbound events are idempotent by `event_id`; outbound events get a strictly increasing per-session `seq`.
* **Call runner** (`calls/base.py`). `CallRunner.run`: budget guard check, `gateway.run` (render with untrusted data wrapped, reserve budget, provider with the spec's deadline, strict-schema validation, one repair at low effort, retries), then local validators, then on any `GatewayError`, timeout, empty output or validator error the spec's deterministic `fallback`, then record cost and write a call-log entry (`ok`, `repaired`, `cache_hit` or `fallback` with the reason). It never raises for a model-side failure. `LiveCallForbidden` is not a `GatewayError`, so a live-mode misconfiguration fails the turn (`turn_failed`) instead of being hidden by a fallback. **A fallback is a failure** (ADR 0015): see [Fallbacks are failures](#fallbacks-are-failures).
* **Budget** (`budget.py`, `config.BudgetPolicy`, `ledger_spend.py`). `CompassBudget`: cap = `COMPASS_LIVE_BUDGET_USD` clamped to at most 3.00 (the owner's ceiling, D-093; a larger, unparsable or non-positive value never widens it); the aim is to finish every live batch under `target_usd` 2.00 (planned and reported against, not enforced by the guard); stop at 95% of the cap (2.85); per session 0.50; `reserve_usd` 0.30 is the amount the owner keeps for manual sessions (declared for the batch plans; the guard does not read it either); integer micro-dollars; `check` raises `BudgetExceeded` (a `GatewayError`, so the runner falls back) when total or session spend plus the estimate reaches the limit or when the estimate is negative (fails closed). In mock mode every cost is 0. **Spend survives a restart:** the counter itself is per process, so in live mode `compose.build_service` starts it from the gateway ledger: `ledger_spend.compass_spent_micros` reads `data/.budget/ledger.jsonl` (setting `LLM_BUDGET_LEDGER`) read-only, adds up the committed cost of every reservation whose spec id starts with `cmp.`, and `CompassBudget.reconcile` adopts that total if it is larger than the counter (a missing ledger is zero; a damaged line is skipped; it never writes or locks). That makes `COMPASS_LIVE_BUDGET_USD` a cap on all Compass spend in the ledger, not on one run. The gateway ledger and the global USD 6.00 cap remain authoritative ([live-llm-budget](../runbooks/live-llm-budget.md)); call contexts use the budget scope `session:<id>`.
* **Config** (`config.py`) is the only module with numbers that logic depends on: `CALL_PROFILES` (effort, output cap, lane, route, timeout for each of the 17 calls), `QuestionPolicy` (Express at most 5 questions, Standard target 7, hard cap 10, Large 6 per module, VOI weights, 20-word questions, 8-word options, exactly 3 options, two failed validations then the fallback card; the legacy engine's budgets), `InterviewPolicy` and `ContextBudgets` (the planner engine's, see [Config of the interview](#config-of-the-interview)), `GatePolicy` (2 probe repair rounds, typed yes at confidence 0.8, required approver role `approver`, 6-turn history slice, 2 back-edge loops), `IntakeLimits`, `BudgetPolicy`. One model, `gpt-6-luna`; every call carries a `lane` (writer, critic, canary) so another vendor can be added later.

## The AI-planned interview

The model decides **what to ask** (specific to this project) and **how to word it**. Code decides **whether a question is allowed** (validators and the auditor), **when to stop** (coverage, budget, fatigue), **what is stored** and **what is shown**. The model never controls the flow. Source: [doc 11 section 17](../architecture-v3/11-discovery-agent-design.md), [ADR 0015](../adr/0015-ai-planned-interview-and-interview-memory.md), D-090 to D-099.

### The engine flag

`InterviewPolicy.engine` is `"legacy"` or `"planner"`. The default is `"legacy"` (the frame engine) until the planner is switched on in Phase 7; the legacy handlers are deleted in Phase 8. `COMPASS_INTERVIEW_ENGINE=legacy|planner` overrides it when the service is built (`compose.resolve_config`; any other value is ignored; `build_service(compass_config=...)` takes a config for tests and the variable still wins). The branch is at handler level in `Service` (`self.interview.active`); the legacy handlers are untouched. `test_the_default_engine_is_still_the_legacy_one_until_the_flip` pins the default. The flag is a scaffold, not a shipped alternative.

### Flow of a turn (planner engine)

1. **Receive.** `Service.handle_event` records the inbound event (idempotent by `event_id`), takes the turn and loads the Brief, the questions and the Interview Memory.
2. **Understand.** A typed or spoken message goes to `cmp.understand_turn` together with the open needs and the fact digest (`InterviewController.understand_text`). An answer to a planned question goes with the exact question, the needs it serves and the digest. A tap on a registry card, or a pick on a planner question about one enumerated need whose label is the registry's, is read by code with no model call. An answer-all form reads its answers in parallel (`understand_concurrency`, 4).
3. **Facts.** Each extracted fact gets the next `FCT-###` id. **Code** verifies its quote against the source text (the typed words, the labels of the chosen options, or the document chunk); a quote that is not found is kept and flagged `unverified_quote`. Slot updates that no fact accounts for become facts too, so the ledger is complete whatever the interpreter returned. A fact that `corrects` an earlier one, or a `contradicts` entry, supersedes the older fact (the newest explicit statement wins; history is kept).
4. **Slots.** `fact_projector` writes each fact's effects through `SlotStore`, the single writer of slots (see [Slots are a view over facts](#slots-are-a-view-over-facts)). The person sees an "I picked up: ..." notice with the values.
5. **Needs status.** Code recomputes, per need, `satisfied`, `partial`, `missing` or `assumed` from the facts' aspects (`engine/needs.py`).
6. **Decide** (`InterviewController`, `interview_policy`):
   * **Follow-up.** For each answered question: if no flag blocks it (`off_topic`, `unsafe`, `declined_category`, `pivot`, `contradiction` have their own paths), the need is not already satisfied, the need is high-impact (catalog impact at least 4) and is `partial` or the answer was flagged `vague`, no follow-up was used for it yet, its depth is below `followup_max_depth` (2) and follow-ups so far are below `ceil(0.4 x base questions)`, the planner is called in mode `followup` with the exact pair and the missing aspects. At most two follow-ups per turn. A second thin answer is **not** chased: the need is assumed with a visible chip.
   * **Next question.** Questions whose needs the facts already satisfy are dropped (the matching cards disappear). The next waiting question is shown, follow-ups first.
   * **After a batch.** When no question is waiting: refresh the rolling summary if the ledger outgrew half of the digest budget, then `stop_decision`, then either a `replan` batch or the end of the interview.
7. **Commit** in one unit of work. The outbound events of the turn are stored in order.

### Round 0: two chained turns

* **Turn 1** (the user's first message): screen the text, understand it, store the facts, run `cmp.situate` for the Situation Profile and the domain hypothesis, emit the `notice` and the `playback` ("Here is what I understood"). No batch exists yet, so `next_question` does not plan inside this turn: it sets an internal `command` event `prepare_questions` with a stable id `int_<24 hex>` (a sha1 of the turn id and the name) and returns "scheduled". The turn commits, so the playback is already in the event log and on the SSE stream.
* **Turn 2** (the internal `prepare_questions` command, recorded in the event log as an inbound `command` with that id, its outbound events carrying it as `turn_id`): `InterviewController.prepare` plans the first batch (`cmp.plan_questions`, mode `initial`, through the pipeline below), merges the planner's hypothesis into the one `cmp.situate` made (`Service._merge_hypothesis`: non-empty fields win, lists merge), emits the `question_batch`, then a `progress` and the first `card`. The session moves to `INTERVIEWING`.
* The whole chain runs inside the one `POST .../events` request: the reply carries the events of both turns. The person can read the playback on the stream while the planner works (ADR 0004 holds: no transaction spans a model call).
* The chain is idempotent. The internal id is derived from the first turn's id, so a retried request does not plan twice, and `plan` looks the batch up by `(mode, inputs_hash)` before spending anything (`test_the_chained_round_zero_turn_is_idempotent_by_construction`, `test_resending_an_event_is_acknowledged_and_ignored`).
* `prepare_questions` is in the `command` names only so it can travel the normal event path. Clients do not send it; sent after a batch exists it does nothing.

### From planner output to shown questions

`engine/question_pipeline.py` (`plan_validated`) turns one planner call into questions that may be shown:

1. `cmp.plan_questions` returns a batch (or its flagged fallback batch, which skips the rest: those cards are made by code from the Needs Registry).
2. **Code validators** (`engine/question_validators.py`, 28 named issue codes) reject what is generic (no project term), repeated (the ledger, by intent, then by overlapping need and text similarity at least 0.8), malformed, over the word limits, in the wrong language, a technology question, a declined or tier C option, leading, with an invented number or brand, or over the batch and group size.
3. `cmp.audit_questions` reviews the survivors; below specificity 3, or any flag, is a rejection.
4. **One repair call** to the planner covers the rejected questions and any must-level or high-impact need that is neither asked, covered nor listed in `assumed_instead`. A repair that itself fell back never replaces a good batch. Whatever is still rejected is **dropped**. A canned question is never substituted silently.
5. Only when nothing at all survives in a mode that must ask (`initial`, `replan`, `deepen`) while needs are open does the engine take the flagged fallback batch.
6. The batch is cut to the wanted size; extras go to the backlog; every planner run is stored as a batch row with its inputs hash, accepted and rejected questions, verdicts, latency and flags.

The model's questions become `Card`s with `frame: "planned"`: ids `Q-###` assigned by code, `group_id`, `need_ids`, `intent`, `unlocks`, `answer_spec`, `followup_hint`, `examples`, `origin` (`planner`, `followup`, `fallback`; `frame` for the legacy engine), `parent_card_id` and `depth` for follow-ups. A batch is **2 to 3 themed groups of 3 to 4 questions** with titles in the user's language. Batch sizes by budget: quick 4 to 5, standard 5 to 7, thorough 6 to 8, always clipped to what is left of the budget.

### Presentation modes, budgets, stopping

* **UI mode.** `one_at_a_time` (default for non-technical users) or `answer_all` (default when the Situation Profile says the person is technical or product-minded). The person switches with the commands `mode_answer_all` and `mode_one_at_a_time`; the choice is kept in `meta.interview` (`ui_mode_set`). In `answer_all` mode the whole batch is marked as asked at once, only the first gets a `card` event and the form is rendered from the `question_batch` event; answers come back in one `batch_answer`.
* **Budgets** (questions including follow-ups): `quick` 5, `standard` 12, `thorough` 25. The person chooses with the commands `budget_quick`, `budget_standard`, `budget_thorough` (stored in `meta.plan.interview_budget`). Without a choice: "just build it" (urgency `just_build`) means `quick`, a Large (enterprise) session `thorough`, anything else `standard`. **"Ask me more"** (`ask_more`) drops the waiting questions, sets the budget to `thorough`, clears the stop reason and plans in mode `deepen`; if the planner has nothing, a `nothing_more` notice says so.
* **Stop rules** (`interview_policy.stop_decision`, in this order): the person said enough (a parameter exists; the engine does not pass it today, "that's enough" is handled by `finish_with_defaults`), **fatigue** (the last 2 answers were all skips, "You decide" or typed answers of at most 2 characters; a tap is never "short"), **budget reached**, **coverage reached** (every `must` need is satisfied or assumed and the turn that finished the batch added no new fact). The reason is stored in `meta.interview.stop_reason` (`fatigue`, `budget_reached`, `coverage_reached`, or "the planner has nothing important left to ask"). On stop the waiting questions are dropped and `Service._assume_required` makes every required slot still empty a visible assumption (catalog default, then the hypothesis, then the first suggested option; listed in "We assumed", never Locked); the pipeline then continues with seeding, probes and review.

### Help, edits, pivots, documents, gaps

* **"I do not understand" / "I do not know."** While a planned question is pending, `route_help` recognises these phrases (English, Hindi, Hinglish; at most 8 words) and `InterviewController.on_help` calls `cmp.rephrase_question`: the first two "I do not understand" requests re-word the question, the first "I do not know" simplifies it (same options, same ids); the next request is not pushed: "You decide" assumes visibly and a `simplified_decided` notice says so.
* **Edit an answer** (`answer_edit`): a new answer version, the facts of the old one superseded (not deleted), the slots they fed rebuilt from the facts that remain, and the waiting questions planned again. Not allowed after approval (an `edit_unavailable` notice; the change flow applies there). Editing during review reopens the review.
* **Pivot** ("actually it is for clinics", flag `pivot`): the earlier facts about the idea and the audience are superseded, `cmp.situate` runs again, a `pivot` notice names the old and new category, the waiting questions are dropped and the planner replans with `pivot_from`.
* **A document or link mid-interview**: its claims become facts (origin `document`, the quote was verified against the chunk by the intake); needs close and waiting questions the facts now answer disappear.
* **A hand-off probe gap** that needs a question becomes one planned question (`replan`, one question; at most two questions per need), so the Brief is never held hostage.
* **A question or an off-topic remark** is answered by `cmp.answer`, then the pending question is shown again.

### Fallbacks are failures

If the planner fails validation after the gateway's one repair, or the call fails, a minimal deterministic card from the Needs Registry is used instead (at most three, for the most important open needs). It is **flagged**: `fallback: true` and `origin: "fallback"` on the card, `used_fallback` on the batch row, `outcome: fallback` in the call log, and one more on `meta.interview.fallback_count`. The same count includes the auditor's heuristic, a rephrase that returned the original question, the summary merge and the Brief compile floor. A fallback of another call (such as `cmp.understand_turn`) is in the call log only. **In a live batch the count must be 0**; any fallback is a bug to fix offline. Mock mode is not live: its questions are labelled `[mock]`, built from the idea's own terms, and the UI is to show a mock banner so a mock session cannot be mistaken for the product.

### Config of the interview

`config.InterviewPolicy` (all code-decided numbers; defaults shown) and `config.ContextBudgets`:

| Setting | Default | Meaning |
| --- | --- | --- |
| `engine` | `legacy` | `legacy` or `planner` (`COMPASS_INTERVIEW_ENGINE` overrides) |
| `quick_max`, `standard_max`, `thorough_max` | 5, 12, 25 | question budgets, follow-ups included |
| `quick_first_batch`, `standard_first_batch`, `thorough_batch` | (4, 5), (5, 7), (6, 8) | batch size range per budget, clipped to what is left |

| `followup_max_depth`, `followup_max_fraction` | 2, 0.4 | follow-up depth per need; follow-ups at most this share of base questions |
| `fatigue_streak`, `fatigue_short_chars` | 2, 2 | consecutive skips, "You decide" or answers of at most this many characters |
| `marginal_new_facts_min` | 1 | a finishing turn that adds fewer facts is "low marginal value" |
| `audit_min_specificity`, `repair_attempts` | 3, 1 | auditor threshold; one repair call, then drop |
| `duplicate_similarity_min` | 0.8 | normalized text similarity that counts as a repeat (calibrate in the live batches) |
| `min_quote_chars` | 3 | shortest quote that can be verified |
| `understand_concurrency` | 4 | parallel `cmp.understand_turn` calls for an answer-all form |
| `project_term_share_min`, `cross_idea_overlap_max` | 0.9, 0.5 | targets for the evals (share of questions with a project term; pairwise overlap across ideas), not read by the engine |
| `min_accepted_share`, `high_confidence_closes_need` | 0.5, 0.8 | declared; nothing reads them yet (need closure comes from the facts' aspects) |

`ContextBudgets` (tokens are estimated as characters divided by `chars_per_token`, 4, with no tokenizer): `project_card` 1500, `fact_digest` 4500 (lowered from 6000 so a planner prompt stays under the gateway's 20,000-character cap on untrusted input, D-099), `needs_table` 2000, `asked_list` 1500, `last_qa` 1500 for the last `last_qa_count` (4) pairs; `compile_ceiling` 60,000 tokens and `compile_chunk_facts` 120 for the Brief compile. `BudgetPolicy` is described under Architecture.

## Interview Memory

Everything a person says is kept, in Postgres, so the Brief can be built from the whole interview and nothing is asked twice. Migration `0002` (Alembic, append-only, with a working `downgrade`) adds four tenant-bound tables to the `compass_*` set; each references `compass_sessions` through the composite key `(session_id, tenant_id)` and cascades when the session is deleted.

| Table | One row is | Notes |
| --- | --- | --- |
| `compass_qa` | one question and its answer, **versioned** | key `(session_id, card_id, version)`; the full `Card` as it was shown, the answer exactly as sent, `custom_text`, `input_mode` (tap, text, voice), status (`open`, `answered`, `skipped`, `you_decide`, `assumed`, `superseded`, `dropped`), batch and group, planner mode, parent question for follow-ups, asked and answered times. An edit adds the next version and marks the old one `superseded` |
| `compass_facts` | one atomic fact, the long-term memory | key `(session_id, fact_id)` with `FCT-###` (never reused); type, statement, topics, entities, `consumers`, confidence, status (`active`, `superseded`, `disputed`, `not_used`), origin (`stated`, `tap`, `assumption`, `document`), source reference, the question or claim it came from, the verbatim `quote`, `unverified_quote`, `supersedes`, `not_used_reason`, `effects`, `aspects` |
| `compass_interview_summary` | the rolling summary | one row per session, replaced on each refresh; topics with decisions, open issues, the person's vocabulary, tone and fact ids |
| `compass_batches` | one planner run | key `(session_id, batch_id)` (`BAT-###`); unique per `(session_id, mode, inputs_hash)`, so a replan with identical inputs is found, not paid for again; the validated output, accepted and rejected questions, auditor verdicts, `used_fallback`, `repaired`, latency, cost |

* **Facts are never deleted.** A database trigger (`trg_compass_fact_guard`, function `compass_fact_guard`) refuses `DELETE` on `compass_facts` while the session exists and refuses any update of `fact_id`, session, tenant, `created_at`, `statement` or `quote`. Status, links and metadata can change; a correction is a new fact that supersedes the old one. The only way facts disappear is deleting the whole session (the cascade). The ports have no delete method either (`FactRepo`, `QaRepo`, `SummaryRepo`, `BatchRepo`).
* **Ports, a fake and Postgres, one contract suite.** The repositories are Protocols in `store/ports.py`. `InMemoryStore` (the fake) and `PostgresStore` both run the one contract suite `store/contract.py` (ADR 0007): `tests/store/test_contract_memory.py` offline, `tests/store/test_contract_postgres.py` against an ephemeral database (marker `integration`), plus `test_store_equivalence.py` (random operation sequences give identical results on both) and `test_migrations.py` (upgrade, downgrade round trip, no drift between models and migrations, the fact guard). Run the integration part with `just compass-test-int`.
* **Ids.** `FactRepo.next_id` and `BatchRepo.next_id` take the session lock and return the highest number plus one over all rows; they reserve nothing, so a caller adds the row in the same unit of work (tested with concurrent writers).
* **The rolling summary** is refreshed after a batch once the active ledger is larger than half of the fact-digest budget, and used only for the facts that no longer fit the digest. It never replaces the ledger, and a summary that would drop a fact id is replaced by the deterministic merge.

## Slots are a view over facts

`SlotStore` stays the single writer of slots. A fact carries `effects` (slot, value, `set` / `add` / `remove`); `fact_projector.project` writes each one through `SlotStore.write`, so the existing rules still apply (an assumption never replaces a user value, a correction keeps the old value in `history`, an explicit removal clears).

* **Provenance.** `Provenance.ref` is the fact id (`FCT-###`) and `quote` the fact's verbatim words (cut at 300 characters). ADR 0013's evidence rule only needs a non-empty `ref`, so a fact-backed slot can be Locked with no change to `Provenance`. The provenance type follows the origin: `stated` is `user_text` (`voice` for a dictated message), `tap` is `user_tap`, `document` is `document`, `assumption` is `assumed`.
* **An unverified quote is never Locked.** A fact whose quote was not found in its source, or that has no quote, is projected as `model_knowledge`: the slot can reach Default, never Locked. Only a fact with a verified, user-sourced quote and status `active` (`Fact.supports_locked`) supports a Locked item.
* **Taps and assumptions are facts too.** A tap's quote is the option label; an assumption has no quote. The ledger is therefore complete.
* **Supersession.** Marking a fact `superseded` or `disputed` runs `reproject`: a slot whose provenance still points at a fact that is no longer active is cleared through the normal removal path (history kept) and the remaining active facts are replayed in creation order. A bad effect value never raises; it comes back as rejected and the fact is kept.
* `GET .../provenance/{item_id}` returns the entry as written: `ref` is the `FCT-###` id and `quote` the words copied into it. Resolving the ref to the whole fact (statement, status, what superseded it) is not built; the question-and-answer list (`GET .../qa`) shows each answer with the facts it produced.

## The Brief

`brief.json`, `schema_version` 1 (`domain/brief.py`). Content sections (`SECTION_KEYS`, the ones the hashes cover), 20 in all:

| Kind | Sections |
| --- | --- |
| Dict sections (catalog field name to a `BriefItem`) | `idea`, `context`, `audience`, `experience`, `access`, `data`, `constraints` |
| List sections (typed records) | `apps`, `roles`, `scope` (features), `references`, `integrations`, `glossary`, `domain_facts`, `assumptions`, `open_questions`, `research_requests`, `assets`, `sources`, `declined` |

Also on the Brief but outside the section hashes: `meta` (session id, mode, situation profile, discovery plan, domain hypothesis, locales, depth profile, `degraded`, `probes`, `probe_rounds`, `approvals`, `interview`), `search_hints`, `summary`, `pitch`, and the bookkeeping `version`, `ids`, `readiness`. Of these, `meta.approvals` (which approver approved which hash, enterprise mode) is also left out of `brief_hash`, because recording an approval must not change the hash it was recorded against. Which keys a dict section holds is data (`catalog/slots.yaml` `brief_path`), not code.

**What the AI-planned interview adds (additive, schema version stays 1; ADR 0015 point 5):**

* **`domain_facts`** is a list section of typed facts (`id` `FCT-###`, `type`, `statement`, `topics`, `entities`, `consumers[]`, `source`, `quote`, plus tier, provenance and status like any item), so domain details that fit no fixed field still reach Research, Blueprint and Design. It is **read-only** for patches (a captured detail is changed by changing the answer: `test_a_patch_cannot_edit_the_details_we_captured`) and its ids belong to the fact ledger, not to the Brief's `IdLedger`. The Brief page has a section **"Details we captured"** (`details`, one read-only row per fact, grouped by topic). The consumer views carry only the facts tagged for that consumer (or `all`), as id, type, statement, topics and entities: never the quote, the provenance or any chat text.
* **`meta.interview`** (`InterviewBlock`) is bookkeeping for audit: `budget`, `ui_mode` and `ui_mode_set`, counts (`questions_asked`, `followups`, `answered`, `skipped`, `assumed`, `batches`), `facts_active`, `facts_not_used`, `facts_unreferenced`, `coverage`, `fallback_count`, `question_ids`, `stop_reason`. It is **popped from the hash and never reaches a consumer view**. Because it can change without the hash changing, `Service._commit` saves a new version when it alone changed.
* **`meta.plan.interview_budget`** (`quick`, `standard`, `thorough` or null) is content: it joins the hash once chosen and is omitted while null.
* **Hash stability.** An empty `domain_facts` is omitted from the canonical JSON and from `section_hashes` (`OPTIONAL_SECTIONS`), a missing section hash on both sides is "unchanged" in `changed_sections`, and a null `interview_budget` is omitted, so a Brief written before these changes keeps its hash and its approvals. A regression test recomputes the hash of a stored pre-change Brief (`tests/domain/test_brief_interview_memory.py`, fixture `brief_before_interview_memory.json`).
* **Compile from the ledger** (`engine/interview_compile.py`, at the start of Brief review): `cmp.compile_brief` gets the entire active ledger (in chunks of 120 facts plus one consistency pass when its estimated size is over 60,000 tokens). In code: an item fills a slot only if the slot is **empty**; a Locked item needs verified quotes; every active fact ends up in `domain_facts`, cited by a slot's evidence, or marked `not_used` with a reason. A fact that is none of these is a defect: it is placed anyway and counted in `meta.interview.facts_unreferenced`. `cmp.compile_text` runs after it and sets the final one-line summary and pitch. The fact-coverage check is a test property and a counted defect in production, not a Gate 1 blocker in the code (`engine/gate.py` has no such rule).

Mock mode has one more property: its compile is the floor (no items), so the slot values in a mock Brief come from the projector and `domain_facts` lists every fact.

The base Brief rules follow.

**Every item** carries `tier`, `provenance[]`, `confidence`, `status` and `history[]`.

* **Tier** (code, tested): `Locked` only if the provenance holds an *evidence* entry (`user_tap`, `user_text`, `voice`, `document` or `org_profile`) with a non-empty `ref` (a turn id or `SRC-###` plus a pointer). `assumed`, `pattern` and `model_knowledge` yield `Default` (value present) or `Open`. `validate_brief` rejects a Locked item without evidence, duplicate or tombstoned ids, dangling `apps`/`roles` references and a tier C feature that is `in` scope.
* **Status** (slot state): `empty`, `assumed`, `volunteered`, `confirmed`, `disputed`. An assumed write never replaces a user-given value; a correction overwrites and pushes the old value to `history`; an explicit negation clears.
* **Ids**: `APP-`, `ROL-`, `FTR-`, `ASM-`, `SRC-`, `RR-`, `Q-`, `CHG-` plus three digits, from the `IdLedger` stored inside the Brief: counters only increase, deletions leave tombstones, renames add aliases. An id is never reused, also across undo.
* **Versions**: an integer `version` that increments on every committed change; a stale writer gets `Conflict`.
* **Hashes** (`domain/hashing.py`): `canonical_json` is sorted-key, compact, UTF-8 with volatile keys (`date`, `at`, `created_at`, `updated_at`) removed. `brief_hash` is sha256 over the whole Brief minus `version`, `ids`, `readiness`, `meta.approvals` and `meta.interview` (and minus an empty `domain_facts` and a null `meta.plan.interview_budget`); it still includes the rest of `meta`, `search_hints`, `summary` and `pitch`. `section_hashes` is one sha256 per content section (a section that is optional and empty has none). Approval binds to the whole hash and the section hashes.
* **Baseline**: the approved version is labelled `B-G1` once and is immutable; a later re-approval is labelled `B-G1-v<version>`. Later edits create new versions plus a "changed since approval" diff.

Feature records use `scope_status` (`in`, `later`, `out`, `unsupported`, `needs-engineering`) because every item's `status` is already the slot state; `FeatureRecord.priority` is `must`, `nice` or `later`; `capability_tier` is `A`, `B` or `C`; `custom: true` marks a feature outside `families.yaml`.

**Consumer views** (`views/consumers.py`): `research`, `blueprint`, `design`, `verify`, built field by field from values only (no provenance, quotes, history, confidence, turn ids or chat text; a property test checks the serialized result). Each view also carries the `domain_facts` tagged for that consumer (or `all`), only as id, type, statement, topics and entities, and only when there are some; `test_consumer_views_carry_the_facts_and_never_the_words_of_the_chat` (`tests/engine/test_interview_flow.py`) checks it end to end. **Readiness** (`views/readiness.py`) is derived from the catalog: a consumer is ready when none of its `must` slots is empty (`ask_if` value comparisons are real conditions, `filled`/`empty` checks only order questions); `should` slots are advisory. **`BriefViewModel`** (`views/build.py`) is the display-ready page: 15 sections (`idea`, `who`, `apps_roles`, `features`, `look`, `access`, `integrations_data`, `limits`, `words`, `details`, `assumed`, `unknown`, `lookup`, `sources`, `cannot_build`; `details` is "Details we captured", read-only rows from `domain_facts`), rows keyed by path, badges with text and icon (`you_said`, `from_document`, `assumed`, `typical`, `suggestion`), header with readiness chips, footer with the approve and change labels and the blockers in the session language.

## State machine

`engine/state.py`: a pure transition table (`TRANSITIONS`, state to trigger to next state). `CHANGING` and `PAUSED` return to where they came from (`SessionRecord.resume_state`); `change_applied` from an approved origin lands in `BRIEF_REVIEW`; `ARCHIVED` has no way back.

| State | Meaning | Table triggers (to) |
| --- | --- | --- |
| `WELCOME` | canned greeting card shown | `start` (INTAKE), `idea_received` (UNDERSTANDING), `documents_received` (INTAKE) |
| `INTAKE` | a first document or link is being read | `idea_received`, `documents_received` (UNDERSTANDING) |
| `UNDERSTANDING` | first idea: profile and hypothesis | `understood` (INTERVIEWING) |
| `INTERVIEWING` | one card at a time | `playback_shown` (PLAYBACK), `queue_empty` (SEEDING) |
| `PLAYBACK` | "here is what I understood" | `playback_confirmed`, `need_more` (INTERVIEWING), `queue_empty` (SEEDING) |
| `SEEDING` | research requests written | `research_seeded` (PROBING), `need_more` (INTERVIEWING) |
| `PROBING` | three hand-off probes | `probes_done`, `gate_open` (BRIEF_REVIEW), `need_more` (INTERVIEWING) |
| `BRIEF_REVIEW` | Gate 1 is open or being prepared | `gate_approved` (APPROVED), `need_more` (INTERVIEWING), `reopen` (BRIEF_REVIEW) |
| `APPROVED` | Brief approved (version and hash) | `reopen` (BRIEF_REVIEW) |
| `CHANGING`, `PAUSED` | side states | `change_applied`, `change_cancelled`, `resume` (back to origin) |
| `ARCHIVED` | `start_over` | none |

Every state also takes `pause` (working states), `start_over` and, from `INTERVIEWING` onward, `change_requested`. The service drives a subset (see Limitations): `documents_received`, `idea_received`, `understood`, `playback_shown`, `queue_empty`, `research_seeded`, `probes_done`, `pause`, `reopen`, `gate_approved`; it sets `INTERVIEWING`, resume and `ARCHIVED` directly. A trigger that is not in the table raises `InvalidTransition` (HTTP 409).

**A first message.** The session starts at `WELCOME` with the greeting and a card of four starts (describe, upload, like an app, just build it). The first idea runs `understand_turn`, then `situate` (profile, hypothesis, depth: `express` when the user asks to just build it, `large` for enterprise, else `standard`; question budget 5, 7 or 10), writes an assumed category from the hypothesis, shows a **Playback** event and asks the first card. After each answer the queue is recomputed. When it is empty the service seeds research (`seed_research`, `lookup_preview`), runs the three probes in parallel (`probe_result` events), compiles the text (`compile_text`) and emits `brief_ready` with `approvable` and the blockers. That is the legacy engine; under the planner engine the first message runs as two chained turns and the questions come in planned batches (see [The AI-planned interview](#the-ai-planned-interview)), while seeding, probes, review and the Gate are the same, with `cmp.compile_brief` running first at review.

## Interview behaviour

The rules below are code (`engine/service.py`, `engine/flows/*`, `engine/voi.py`) with their numbers and cue phrases in data (`flows.yaml`, `config.py`, `catalog/`). They are covered by the scenarios in `tests/scenarios/data` and the unit tests in `tests/engine/flows`. They were written for the frame (legacy) engine. Under the planner engine the rules that choose or shape a frame card (proposed, not asked; the follow-up for an empty required slot; the priority card; the app-structure card) do not apply, because the planner and the interview policy decide the questions. "Just build it" (Express) means the `quick` budget there, and the closing step that assumes every required slot still empty is the same. The rules that react to a typed message or to a Brief edit (references, voice read-back, phased apps, locked-edit preview, typed back-edge, re-seeding, re-approval, corrections) run in both.

* **Proposed, not asked.** Once the engine has a value from the hypothesis, the kind of app (`confirm_kind_of_app`, slot `idea.category`) and the roles (`roles`, slot `roles.list`) are shown in the playback for correction and listed in "We assumed"; they are not asked as cards. A hybrid idea (two or more likely families) still asks which kind is primary. (`PROPOSED_NOT_ASKED`.)
* **Express ("just build it").** Depth `express`, question budget 5. When the queue is exhausted the service asks no follow-ups: every required slot still empty is assumed from the catalog default, else the hypothesis (first business-model candidate; up to three non-custom likely features), else the first, suggested option of the slot's card. These are `assumed` with `pattern` provenance, listed in "We assumed", never Locked.
* **Follow-up for an empty required slot.** A required slot with no catalog default that is still empty after its frame was asked gets one follow-up card, at most two asks per slot. Past the question cap (10; the Express budget; for Large 10 plus one module's worth) only must-confirm slots (`auth.methods`, `auth.account_model`, `integrations.wanted`, `data.sensitive`) and Large depth bypass the cap. Follow-up answers merge into list values (de-duplicated). `idea.subcategory` is never asked: it is derived (assumed) from the hypothesis or the category. An empty checklist on a required slot is not a decision: the typical items (up to three) are assumed and a notice says so.
* **Priority card.** "Everything is a must" (or every feature ticked) opens one ranking card, "If you launched with only five features, which?" (needs at least two features, shows at most 14 chips). The first five ranked are Must, the rest become `later` (the Phase 2 backlog). It never adds a feature.
* **References.** A named app ("like Swiggy") is stored `assumed`, never Locked on a mention. "I own X" opens a confirm card (is it yours, or an app you like). "Exactly like X, same logo" gets one patterns-only warning. One quick-form card (at most four references) asks what to borrow and what to avoid.
* **Voice.** A dictated run-on is split into atomic statements by rules (joiner words and fillers are data); names, numbers and places are echoed; three or more statements, or anything ambiguous, get a numbered read-back the user edits ("remove 2"; items it cannot tell apart are never cleared).
* **Phased apps (DC-11).** Five or more apps: the first two named go into the first release; the rest are kept as scope features with status `later` and source `later_phase_app`, and the explanation lists up to six names.
* **App structure.** The "which apps" card offers structure codes (`one_app`, `customer_and_staff`, `app_plus_admin`); `engine/app_structure.py` expands the picked code into app records with localised names and purposes from the catalog strings.
* **Corrections and Locked edits.** During the interview a typed correction with a stated value applies at once (the latest explicit statement wins). In review or after approval a change request goes through the change flow. A `brief_edit` or chat change that rewrites a Locked value **that the user confirmed with a tap on a card** (a `user_tap` in its provenance) does not apply at once: a one-question card with an **impact preview** (the consumers the catalog names for that slot, at most four) applies it on "Yes, change it". Words the user typed themselves (volunteered, or edited in the Brief) and anything not Locked stay freely editable. A junk answer to a flow card (nothing chosen) shows the card again and changes nothing.
* **Typed back-edge.** `Service.reopen_slot(caller, session_id, slot_id, reason)` lets a later stage (research) reopen ONE slot with one targeted card: the reason, the current value, up to three alternatives from `cmp.make_variants` and "Keep what I said". At most two per session (`max_back_edge_loops`), then a notice. It is a method for the flow, not an HTTP route.
* **Re-seeding.** Research requests are rebuilt only when an op touches `idea.category`, `idea.subcategory`, `context.geo`, `audience.*`, `references` or `scope.*`; a wording edit does not re-seed (so undo stays exact).
* **Re-approval.** Approving the same, unchanged approved Brief again is a no-op (the approval message, no second baseline).

## Documents and links

`mde_compass.intake` (`parsers`, `chunking`, `url_reader`, `htmltext`, `pipeline`, `errors`) plus `engine/document_flow.py` and `engine/document_map.yaml`. Everything a document says is **data** (hard rule 5): never executed, followed or obeyed; macros, embedded files and links in a file are never opened.

* **Inputs.** A file (`POST /sessions/{id}/uploads`, multipart, one file per request, `UploadAdded` inside the service), a link (`link_added`), or a pasted message over 3,000 characters (`pasted_text_is_document_over`). Formats: PDF (text layer only; a page without one is marked unreadable and is never OCRed), DOCX, XLSX, PPTX, CSV, TXT, MD, EML. Images are accepted as sources with no text: the gateway has no image input. The type is decided by extension and magic bytes (a mismatch is rejected), archive members are checked against a decompressed-size ceiling, hidden text (DOCX hidden runs, PPTX hidden shapes and slides, hidden sheets) is dropped, zero-width and control characters are stripped, and no regex runs over document text.
* **Limits** (`IntakeLimits`): 15 MB per file (the API answers 413 `too_large` while reading, never after), 10 files and 60 MB per session, 300 pages, 5 links, chunks of 3,000 to 4,000 tokens (characters divided by 4), 4 concurrent reads; a link has a 10 s deadline, a 2 MB body, 3 redirects.
* **Pipeline** (`ingest_bytes`, `ingest_text`, `ingest_url`): limits and sha256 de-duplication, parse, structure-aware chunking with source pointers (`page 3`, `heading: Payments`, `sheet Roles!A1:D9`, `rows 2-40`; a table row is never split, its header repeats; an unreadable page is its own empty chunk and counts against coverage), redaction (`mde_core.redact`), `cmp.read_chunk` per chunk, `cmp.merge_claims` over the statements, then a plain summary such as "read 100%; 4 statements; 2 need confirming; 0 conflict; 1 open question". It never raises: a failure comes back as a rejected result with a plain message, and one bad file never stops the others. Codes: `password_protected`, `corrupt`, `unsupported`, `too_large`, `too_many_pages`, `too_many_files`, `session_too_large`, `too_many_urls`, `private_link`, `blocked_url`, `too_many_redirects`, `fetch_failed`. A duplicate is explained ("... is the same as a file I already have (SRC-001); I kept the first one"): every upload gets a fresh event id so the duplicate is not swallowed by event idempotency.
* **SSRF-safe URL reader.** http or https only, no credentials, ports 80, 443, 8080, 8443; IP literals in every spelling an OS accepts are understood (decimal, hex, octal, short forms, IPv6, IPv4-mapped); single-label and internal names are refused; **all** resolved addresses must be public (private, loopback, link-local, carrier-grade NAT, cloud metadata and their IPv6 forms are blocked); the checks run again at every redirect hop (the fetcher never follows redirects itself) and the connection is pinned to the validated address. Content types `text/html`, `text/plain` and `application/pdf` only; scripts and hidden elements are dropped; a 401, 403 or sign-in bounce is `private_link`.
* **Claims to Brief writes** (`document_flow.plan_from_claims`, map in `document_map.yaml`): requirement to `scope.features`, user_or_role to `roles.list`, exclusion to `scope.must_not`, constraint to `constraints.must_use`, glossary_term to `glossary.terms`, business_context and goal to `idea.problem_value`. Only `used` claims are written, as `volunteered` with `document` provenance (`ref` = source id plus pointer, the verbatim quote), so they can be Locked. List slots are extended, never overwritten; a single-text slot the user already filled is never overwritten (**chat beats documents**). Open issues ("TBD") become non-blocking open questions (at most five); claims that need confirming become ONE summary open question; conflicting claims are counted and not written. Each source becomes a `SourceRecord` (Locked, `document` provenance). A document that tries to instruct the assistant is noted ("document instruction ignored") and otherwise treated as words. A first document in `WELCOME` moves the session to `INTAKE` and then runs the normal first understanding.

## Gate 1

* A `gate_decision{approve}` (HTTP `POST /gate`, or a typed yes) is accepted only when there is **no blocker and the supplied version and hash match the current ones**; an approval without version and hash is refused. If `section_hashes` are supplied they must also match.
* Blockers (each a catalog string, shown in the user's language): a `must` slot is still empty; a high-impact assumption (catalog impact at least 4 or risk high) has no explicit decision, **silence never approves**; a hand-off probe has not passed (unless the Brief is flagged `degraded` after 2 repair rounds); a blocking open question; version or hash mismatch; in enterprise mode a required approver role (`approver`) has not approved this hash (the approval is kept in `meta.approvals`, which `brief_hash` ignores, so approving does not move the hash; contributors `approver` and `commenter` are created with an enterprise session).
* A typed yes (`classify_yes`) counts only in `BRIEF_REVIEW`, when the gate is open, the message is exactly an approval phrase (English, Hindi or Hinglish, fillers allowed, at most 8 words, no hedge); "ok but change the colour" is a change request; anything else is unclear.
* Approving the same unchanged Brief again is a no-op. On approval: state `APPROVED`, version labelled `B-G1` (first time), `brief_approved` event, consumer views built (`research`, `blueprint`, `design`, `verify`) and passed to the `HandoffPort` after the commit. `GET /handoff` serves the same views from the approved version and answers 409 before approval.
* An edit of an approved Brief (any change source) voids only the sections whose hash moved, the session returns to `BRIEF_REVIEW` with a "changed since approval" notice, and approval needs a fresh decision.

## Changes and undo

Every content change after the first draft is a `ChangeSet` of `PatchOp`s (`set`, `add`, `remove`, `clear`), addressed by one path grammar: `<section>.<key>` for dict sections (`idea.summary`), `<section>.<ID>[.<field>]` for list sections (`scope.FTR-004.priority`). `engine/patch.py` applies ops to a copy, validates, assigns `version + 1`, records provenance (a user edit becomes `confirmed` with the actor's evidence; a non-user actor can never overwrite a user-given value), computes the **voided sections** (sections whose hash moved) and builds `inverse_ops`. Sources: `ui_edit` (`brief_edit`), `feedback` (`brief_feedback` with a reason chip), `chat` (typed change request, via `cmp.interpret_change`), `assumption` (`assumption_decision`), `lookup` (`lookup_edit`), `undo`, `engine`. A change to `idea`, `context`, `audience`, `scope` or `references` re-seeds research; the probes whose sections moved are re-run. "I don't want this assumption" or a "wrong tone" chip opens a three-variant card (`cmp.make_variants`); a request that is ambiguous returns an either/or card instead of ops. Touching a Locked item is allowed and flagged. **Undo** (`command{undo}`) applies the inverse ops of the latest change set as a new version (`undoes` points at the reverted `CHG-` id); history is never rewritten. `GET .../brief/diff?from=&to=` returns the entries between any two versions.

## API and events

Endpoints: [api/compass.md](../api/compass.md). In short: `POST/GET /v1/compass/sessions`, `GET /sessions/{id}`, `POST /sessions/{id}/events`, `GET /sessions/{id}/stream` (SSE), `GET /sessions/{id}/brief`, `/brief/view`, `/brief/versions`, `/brief/diff`, `/history`, `/qa` (every question with its answer and the facts it produced), `/provenance/{item_id}`, `POST /sessions/{id}/gate`, `GET /sessions/{id}/handoff`, `/calls`, `/budget`, `/strings/{lang}`, `POST /sessions/{id}/uploads` (multipart, one file per request, answers an `EventAck`), plus `/healthz` and `/readyz`.

**Inbound events** (discriminated by `type`, each with a client-chosen idempotent `event_id`, 1 to 64 characters of `A-Za-z0-9_.:-`): `user_message` (text up to 20,000 characters, `input_mode` text or voice, optional `lang_hint`), `card_answer` (`card_id`, `value` = an option id, a list of ids, ordered ids or a form object, optional `custom_text`), `card_skip`, `card_you_decide`, `card_back`, `batch_answer` (the answers of a whole batch form, planner engine), `answer_edit` (edit an earlier answer, planner engine), `upload_added`, `link_added`, `command` (`undo`, `back`, `pause`, `resume`, `start_over`, `finish_with_defaults`, `show_what_you_know`, `ask_more`, `prepare_questions` (internal), `mode_answer_all`, `mode_one_at_a_time`, `budget_quick`, `budget_standard`, `budget_thorough`), `brief_edit` (`item_id` path, `value`), `brief_feedback` (`target`, `reason`, `text`), `assumption_decision` (`id`, `accept` or `change`, `value`), `lookup_edit` (`add` or `remove`), `contributor_switch`, `gate_decision` (`approve` or `request_changes`, `version`, `brief_hash`, `section_hashes`). A repeated `event_id` is acknowledged and ignored (`duplicate: true`).

**Outbound events**: `assistant_message` (text, language, "I picked up" chips), `card` (the planner engine's cards also carry `batch_id`, `group_id`, `need_ids`, `intent`, `unlocks`, `origin`, `parent_card_id`, `depth`, `rephrased`), `question_batch` (a planned batch with its groups, planner engine), `playback` (editable rows plus what is unclear), `notice` (code, text, chips, severity), `progress` (stage, n, of about), `brief_patch` (change set id, versions, summary, ops, voided sections, undoable), `brief_ready` (version, hash, section hashes, `approvable`, blockers), `brief_approved` (version, hash, baseline), `lookup_preview` (research requests), `probe_result` (kind, passed, gaps, round), `budget_warning`, `error` (code, message), `assistant_delta` (reserved). `budget_warning` and `assistant_delta` are defined but never emitted today. Field by field, with the new events, see [api/compass.md](../api/compass.md).

**SSE replay.** Every outbound event is stored with a per-session `seq`; the stream frame `id` is that `seq`. A client that reconnects with `Last-Event-ID: <n>` (or `?after=<n>`) receives everything after `n`, then the live tail; `follow=false` replays and closes. Idle streams back off between polls, send `: keepalive` every 15 s, close after 900 s and are capped at 8 per caller.

## Safety

`safety/screen.py` runs on every free-text field before storage (`Service._sanitize`) and before any prompt: cut to a maximum length, strip hidden characters, redact secrets (`mde_core.redact`), mask card-like numbers (13 to 19 digits, Luhn valid, last four kept), then detect on the redacted text: injection phrases (noted, never obeyed), unsafe requests (illegal, harmful, abuse) and declined categories (the 8 `declined` capabilities, with a polite alternative; a companion app for a declined thing is allowed, and benign phrases such as "game plan" cancel the match). Phrase tables are data (`safety/lexicon.yaml`). A declined request is recorded in `declined[]` and shown, never built. Web, upload and document text is data: no call has tools (hard rule 5). Money is integer micro-dollars; IDs are prefixed ULIDs.

API protections: dev bearer token compared in constant time, identical 401 for every auth failure, tenant isolation by `tenant_id` (a foreign id is a 404), request body limit 256 KB (`COMPASS_MAX_BODY_BYTES`), `X-Request-Id`, security headers (CSP, nosniff, no-referrer) on every response, a refusal to bind a non-loopback host with dev auth.

## Known limitations

* **No vision and no streaming through the gateway** (`ProviderRequest` is text only). Images are accepted as sources with no text, a PDF page without a text layer is reported unreadable (never OCRed), and `assistant_delta` is never emitted.
* **No live evidence.** The live smoke driver exists and has an offline twin test, but this page has no live measurement: call timing, token use, cost, the effect of the real model on question wording and the measured numbers above are all from mock mode. Not built or not run: the live batches (A is the smoke driver; E planner quality, F full interviews and G rich input and language are planned for the planner engine and wait for the owner's decision on the second key), cassettes for Compass, prefetch (`prefetch_enabled` is off), a `ChainedRegistry` gateway hook.
* **The planner engine is not the default yet.** `InterviewPolicy.engine` is `legacy` until Phase 7; the legacy path (and `cmp.write_card` with it) is deleted in Phase 8. Until then both paths are in the code.
* **Declared but unused.** `InterviewPolicy.min_accepted_share` and `high_confidence_closes_need` (doc 11 section 17.5 says a high-confidence fact closes its need; the code closes a need from the facts' aspects instead), `BudgetPolicy.target_usd` and `reserve_usd` (nothing in the guard reads them), the planner mode `simplify` (the engine uses `cmp.rephrase_question` for "I do not know"), the `sections` argument of `cmp.compile_brief` (the engine chunks by facts), and the `user_said_enough` stop reason ("that's enough" goes through `finish_with_defaults`).
* **`meta.interview.fallback_count` is narrower than "every fallback".** It counts the planner, auditor, rephraser, summary and compile fallbacks; a fallback of `cmp.understand_turn` or any other call is only in the call log.
* **The compile summary and pitch are overwritten.** `cmp.compile_text` runs after `cmp.compile_brief` (`Service._open_review`) and sets the final summary and pitch.
* **Hand-off is a stub.** `compose.build_service` wires `LoggingHandoff` (logs and keeps the delivered views in memory); nothing consumes the Brief yet. `reopen_slot` is likewise a method waiting for a caller.
* **The service drives a subset of the state table.** `CHANGING` and several triggers (`start`, `playback_confirmed`, `need_more`, `gate_open`, `change_requested`, `change_applied`, `change_cancelled`) exist in `engine/state.py` but `Service` applies changes and edits inside the turn without entering `CHANGING`.
* **`brief/view?lang=`** is validated but not applied: the real `Service.brief_view` has no language parameter, so the view uses the session locale.
* **`SessionSummary.question_n` and `question_of_about`** are always 0; the progress counter is on the card (`progress`) and the `progress` event.
* **`footer.approvable` in the view model** is true outside `in_review`; use `header.status` or the `brief_ready` event.
* **Never emitted:** `budget_warning` (defined and handled by the UI, no engine code raises it). `CompassBudget.reconcile` is called once, at start-up in live mode, not on every call: spend by other processes during a run is not seen until the next start.
* **Mock readers are heuristic.** The deterministic fallback of `cmp.read_chunk` types sentences by keyword; for example a refund rule can land under roles. The model path adds quote and injection checks on top, but only the live smoke can show how good the real reader is.
* **Windows is unverified.** psycopg's async mode needs a selector event loop; the Context API's launcher sets the policy before any loop exists, `python -m mde_compass` does not (the store engine sets it on creation, which happens inside uvicorn's running loop). Compass was built and run on macOS; PostgreSQL mode is exercised by the integration tests, the in-memory mode by everything else.
* **Fixed since the first version of these pages:** the budget endpoint (the service attribute is now `budget_guard`), the enterprise approval hash (`meta.approvals` is excluded from `brief_hash`).
